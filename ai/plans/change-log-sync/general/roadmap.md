# Change log и синхронизация устройств

Автор: OpenCode, zai-coding-plan/glm-5.3, 2026-11-06

## Зачем

Цель — согласованное поведение нескольких устройств (вкладки и браузеры веб-клиента, в перспективе
мобильные клиенты): изменения, сделанные на одном устройстве, становятся видимы на остальных без
перезагрузки страницы, а одновременное редактирование одной сущности с двух устройств не приводит к
тихой потере чужих правок.

**Что уже есть.** План `ai/plans/freem-events.md` (закрыт 2026-10-20) привёл подсистему событий к
типизированной схеме: все 17 типов изменений (activities, records, running records, tags, users)
публикуются вместе с мутацией и несут снапшот состояния «после изменения» (`EventPayload`); запись
идёт в той же транзакции, что и операция, ошибка записи откатывает операцию. Running records
консистентны по построению: идентификатор записи = идентификатор пользователя, PK на `user_id`, старт
нового таймера авто-останавливает предыдущий, старт/стоп сериализуются per-user локом в Redis. Redis
есть во всех окружениях (сейчас используется только для локов).

**Чего не хватает** — всё, что между «изменение закоммичено в БД» и «другое устройство узнало об этом»:

1. **Порядок и курсор.** `OccurredAt` — UTC с точностью до секунды, `EventId` — случайный GUID,
   сортировка `(OccurredAt DESC, Id DESC)`, пейджинг — offset/limit. Запросить «всё после X»
   невозможно; keyset по `(OccurredAt, Id)` некорректен: при двух мутациях в одну секунду порядок
   определяется случайным id, и событие, вставленное позже, может оказаться до курсора и потеряться
   навсегда.
2. **Дельта-эндпоинта.** `GET api/v1/events` — читалка для аудита (хвост, offset-пейджинг).
3. **Транспорта и реакции клиента.** Ни поллинга, ни SSE/WebSocket. Каждая страница фронтенда
   загружает данные при монтировании и рефетчит вручную после собственных мутаций; настройки
   пользователя грузятся один раз (смена часового пояса на одном устройстве не подхватывается другим
   до перезагрузки страницы).
4. **Защиты от потери обновлений.** `RowVersion` (`[Timestamp]`, xmin) есть на всех сущностях в БД,
   но не выходит в DTO — обновления работают по принципу last-writer-wins, второй Device молча
   затирает правки первого.

**Ключевая идея** — сменить роль журнала: из аудита «без потребителя» в per-user change log
(CDC-паттерн, как Debezium/WAL: снапшот состояния после изменения), на котором строится курсорная
синхронизация устройств. Ориентир — устройство логов в крупных системах (Kafka, EventStoreDB,
Postgres WAL): порядок назначает единственный писатель в момент записи, а не часы; позиции плотные и
монотонные в рамках стрима; чтение — catch-up (дельта по курсору) и live (push); доставка
at-least-once с идемпотентным применением на клиенте.

**Почему сейчас можно менять всё.** Журнал не используется на проде и не имеет потребителей: таблицу
можно пересоздать, имена и контракты — переименовать. Ровно до появления sync-клиента payload
остаётся свободным для изменений; с его появлением он становится контрактом — отсюда поле версии
payload с первого дня.

**Offline** (работа без сети, очередь мутаций) — отдельная следующая инициатива, сразу после этого
плана. Здесь закладывается совместимый с ней фундамент (см. решения ниже), детали — за следующим
планом.

## Принятые решения

Все решения зафиксированы в обсуждении с пользователем 2026-11-06.

1. **Переименование.** Запись журнала переименовывается `Event` → `Change`, журнал как целое —
   `ChangeLog` (`IChangeLogRepository`, `ChangeRecorder`, страница «Change log», таблица `changes`).
   Слово «Event» освобождается под будущие domain events, чтобы не получить лок имён, когда
   появятся intent-события. Строки типов (`activities.created` и т.п.) не меняются — это типы
   изменений.
2. **Природа записей.** Change log — CDC-feed со снапшотами «после изменения», не domain events и не
   event sourcing: сущности остаются источником истины, перестроение состояния из журнала не
   предусматривается. Строгость нумерации при этом как в event sourcing — на неё ложится
   синхронизация.
3. **Порядок.** Стрим = пользователь. Плотная монотонная per-user нумерация (`number`), номера
   назначаются в транзакции операции под блокировкой строки счётчика (таблица `change_counters`,
   `UPDATE ... SET last_number = last_number + n RETURNING`; импорт берёт диапазон одним запросом).
   Видимые номера пользователя — всегда плотный префикс: дыр и «номеров в полёте» не бывает by
   construction, курсор всегда безопасно двигать. Глобальный bigserial отвергнут: номер раздаётся при
   INSERT, а видим при COMMIT — при конкурентных записях одного пользователя читатель видит номер
   N+1 раньше N, двигает курсор и навсегда теряет событие N.
4. **`number` — деталь реализации хранилища.** Наружу (доменные контракты, API, клиент) торчит
   только `ChangeId`; курсор синхронизации = id последней применённой записи; фильтр репозитория
   получает `After: ChangeId?` и сам резолвит id → number. Школа непрозрачных курсоров (GraphQL
   Relay, GitHub/Slack), а не публичных позиций (Kafka offset, EventStoreDB eventNumber): у записей
   есть собственная идентичность, и id-адресация покрывает всё. Публикация number в будущем —
   аддитивное изменение, «переобуться» дёшево; изъятие — ломающее, поэтому выбрано направление «сначала
   не публиковать».
5. **Правила курсора.** «After = все изменения позже указанного в порядке лога, без пропусков» —
   явное обещание сервера в контракте. Неизвестный или чужой курсор → явный ответ «курсор невалиден»
   → клиент делает полный resync. (С публичным number коварнее был бы кейс «курсор впереди головы»
   после пересоздания таблицы — молча пустой ответ; с id-курсором такой ловушки нет.)
6. **Идентификаторы.** GUID N-формата (`Guid.NewGuid().ToString("N")`) остаётся: идентичность,
   адресация, пермалинки. Временной семантики у id нет и не закладывается; ULID не вводится:
   сортируемость не нужна (порядок даёт number), для будущей клиентской генерации id энтропии GUID
   достаточно.
7. **`OccurredAt` — метаданные**, не ключ порядка; точности до секунды достаточно.
8. **Версия payload.** Поле `version` (int, с 1) у каждой записи с первого дня — после появления
   sync-клиентов payload становится контрактом.
9. **Миграция.** Пересоздание таблицы с нуля, без бэкфилла: прода и данных нет.
10. **Один журнал на обе роли.** Аудит читает хвост (в порядке лога по убыванию, фильтры, offset),
    синхронизация читает вперёд (`after`, по возрастанию, keyset по индексу `(user_id, number)`).
    Двух хранилищ/журналов не появляется.
11. **Доставка поэтапно: поллинг → SSE.** Данные всегда тянутся REST-дельтой; SSE — только триггер
    «появились изменения», тогда один код применения данных, а поллинг остаётся fallback'ом.
    Триггеры поллинга: интервал + focus/visibility + после собственных мутаций.
12. **SSE-механика.** Уведомление публикуется после коммита (on-commit колбэки в
    `StorageTransactionRunner`; изнутри транзакции нельзя — получилось бы «уведомление есть, строки
    нет»), fan-out через Redis pub/sub per-user (безопасно при нескольких инстансах API), клиент —
    fetch-based SSE с заголовком `Authorization` (EventSource заголовки не умеет), `Last-Event-ID` =
    курсор. Reverse proxy не должен буферизовать ответ (`X-Accel-Buffering: no`).
13. **Применение на клиенте — invalidate & refetch.** Изменение → какая коллекция затронута → рефетч
    видимых данных; снапшоты в кэши — позже точечно, где понадобится мгновенность. У статистики
    собственных записей журнала нет — обновляется рефетчем при records-изменениях. Применение
    идемпотентно: собственные мутации приходят из журнала повторно, это безопасно. Непонятный тип
    или версия → рефетч затронутой сущности; невалидный курсор → полный resync.
14. **Оптимистичная конкурентность.** `EntityVersion` VO поверх EF `[Timestamp]` (xmin): обновления
    обязаны нести исходную версию, несовпадение → 409 + текущее состояние сущности, разрешение
    конфликта на клиенте. Per-field merge не делается. Счётчик нумерации — отдельная таблица, не
    колонка `users`: bump колонки шевелил бы xmin пользователей и порождал ложные 409 на этапе 4.
    Running records не затрагиваются — там уже лок и PK на `user_id`.
15. **Мульти-вкладки.** На этапе поллинга вкладки опрашивают независимо; с SSE — один коннект на
    браузер (владелец выбирается через Web Locks, прецедент — сериализация refresh-токена в AuthClient
    StashIt) с fan-out через BroadcastChannel.
16. **Непротекание абстракций.** Назначение номеров, счётчики, pub/sub — внутренности своих слоёв;
    наружу — только доменные VO. Хранилище-специфичное наружу — только через VO и по отдельному
    обоснованию, таких решений без обсуждения не принимать.
17. **Offline-закладки.** Несущее для офлайна: курсорная петля «догнал дельту / полный resync» (это и
    есть поток переподключения офлайн-клиента), идемпотентные снапшоты, version/409 как детектор
    конфликтов офлайн-правок. Останется за следующим планом: клиентская генерация id при создании (в
    контрактах не закреплять «id генерирует только сервер»), очередь мутаций с дедупликацией при
    replay, UI разрешения конфликтов.

## Этапы

1. **Фундамент change log.** Переименование Event → Change/ChangeLog во всех слоях (домен, сущности,
   хранилище, use case'ы, API, клиент, тесты); пересоздание таблицы с per-user плотной нумерацией
   (`change_counters`, unique-индекс `(user_id, number)`), версией payload и курсорной дельтой в
   репозитории и API. Объём — структурная перестройка, широкий ревью-след по всему решению.
   Готовность: дельта-запросы по курсору работают, имя «Event» в решении не остаётся.
   → фактура в `ai/plans/change-log-sync/stages/01-change-log-foundation.md`.
2. **Синхронизация в вебе (поллинг).** `ChangesClient`, `SyncProvider` с петлёй поллинга (интервал +
   focus/visibility + после собственных мутаций), invalidate & refetch коллекций, реакция на
   `users.settings_changed`, полный resync при невалидном курсоре; попутно страница просмотра журнала
   (закрывает пункт `tasks.md` о просмотре событий). Объём — средний, в основном фронтенд.
   Готовность: два устройства/вкладки сходятся без перезагрузки.
   → фактура в `ai/plans/change-log-sync/stages/02-web-sync.md`.
3. **SSE-доставка.** On-commit колбэки в `StorageTransactionRunner`, публикация в Redis pub/sub
   per-user, стрим-эндпоинт (fetch-based SSE), поллинг как fallback, один коннект на браузер
   (Web Locks + BroadcastChannel). Объём — инфраструктурный, средний; этап 2 сохраняет ценность как
   страховочный путь. Готовность: изменение на втором устройстве проявляется за секунды, обрыв
   стрима незаметен для пользователя.
   → фактура в `ai/plans/change-log-sync/stages/03-sse-delivery.md`.
4. **Оптимистичная конкурентность.** `EntityVersion` в контрактах обновлений, 409 с текущим
   состоянием сущности, обработка конфликта на фронтенде. Объём — точечный по слоям, но с ломающими
   изменениями контрактов обновлений. Готовность: тихой потери правок при редактировании с двух
   устройств нет.
   → фактура в `ai/plans/change-log-sync/stages/04-optimistic-concurrency.md`.

Этапы последовательны: 1 — фундамент для всех остальных; 2 даёт первую пользовательскую пользу; 3 —
ускоритель на готовой базе; 4 независим по ценности, но опирается на переименование из этапа 1.
