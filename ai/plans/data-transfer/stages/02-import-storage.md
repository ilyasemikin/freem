# Этап: модель импорта и хранилище

Автор: Claude Code, claude-sonnet-5-5, 2026-10-23

См. общий контекст и место этого этапа: `ai/plans/data-transfer/general/roadmap.md` (этап 2).

## Зачем именно так

Разбор файла (этап 3) должен сохранить результат в БД, а применение (этап 4) должно работать с сохранёнными строками постранично и «по всем сразу», переживая повторные запросы и сбои. Поэтому здесь
нужны сущность импорта со статусом и атомарными переходами, строки импорта, которые читаются постранично, и сохранённое соответствие источника Freem. Парсеры, API и
применение сюда не входят: этап даёт хранилище и домен, на которых они строятся.

## Зафиксированные факты

Проверено чтением кода (`source`):

- Модель результата разбора уже есть (этап 1): `ImportParseResult` (до 2026-10-23 `ImportDocument`) → `ImportTag`, `ImportActivity`, `ImportRecord` (`Name`, `Description`, `ActivityIds`, `TagIds`, `Periods`) → `ImportRecordPeriod`
  в `Freem.Domain.Entities/Import`; id из файла — `ImportActivityId`/`ImportTagId`/`ImportRecordId` в `Freem.Domain/Import` (непрозрачные строки, `Generate` у них нет).
- Агрегаты Freem ссылаются друг на друга только по Id; `Id`-типы создаются через `Generate()` (пример: `RecordId`). Репозиторий на агрегат (`ITagRepository`: `Create/Update/Delete/FindById/FindAsync(filter)`),
  результат `Result<…, Error>`, постраничное чтение `AsyncBatch<T>` через фильтры с `Limit`/`Offset`.
- Хранилище: EF Core, `DatabaseContext` с `DbSet` на сущность, конфигурации в `Database/Entities/Configurations`, имена таблиц и ограничений в `EntitiesNames`, `IAuditableEntity` (`CreatedAt`/`UpdatedAt` проставляет
  `SaveChangesAsync`), `IRowVersionableEntity` (`xmin` через `[Timestamp]`). Строки записи периодов — отдельная таблица `RecordPeriodEntity` (`StartAt`, `EndAt`, `TimeZoneOffsetTicks`, `Description`).
- Каскад: `TagEntity`→`UserEntity` с `DeleteBehavior.Cascade`; удаление пользователя делает `ExecuteDeleteAsync` (`UsersRepository`). Других `ExecuteUpdate`/`ExecuteDelete` в хранилище нет: атомарных
  переходов статуса и пакетных обновлений сегодня нет, это новая механика.
- Миграции: `Freem.Domain.Storage.PostgreSQL.Migrations/Instances`, последняя `20261021014425_ActivityColor`; применяются контейнером `postgres-migration`.
- События: `EntityType` (`Activity, Record, RunningRecord, Tag, User`), `EventTypes` с группами по сущностям, публикация через `EventProducer` в use case'ах (репозитории события не пишут).
- Образец статусов в StashIt: `Idle → Parsing → Parsed`, `Parsed → Converting → Parsed`, переходы атомарные (CAS по текущему статусу), в `Idle` назад только при явном сбое
  (`docs/statement-parse-convert-rule-engine.md`).

## Один-два иллюстративных примера (не исчерпывающий список!)

- Атомарный переход: `UPDATE import_documents SET status = 'Parsing' WHERE id = @id AND status = 'Created'`; ноль затронутых строк означает, что переход уже занят, и репозиторий возвращает ошибку конфликта состояния.
- Постраничное чтение строк: `ORDER BY first_start_at, id OFFSET @o LIMIT @l` по документу, чтобы список с тысячами строк не загружался целиком.

## Направление решения (не пошаговая реализация)

Согласовано пользователем 2026-10-23:

- **Агрегат и строки.** `ImportDocument` (Id, UserId, `FormatKey`, имя файла, часовой пояс разбора, статус, найденные в файле активности и теги с решениями) загружается целиком и маленький. `ImportRow` входит в агрегат
  и доступна только через его репозиторий, но вместе с документом не загружается, а читается постранично (их тысячи).
- **Строка импорта** оборачивает уже существующий `ImportRecord` (ключ источника, название, описание, ключи активностей и тегов, периоды) и ничего не добавляет: строка неизменяема, без статуса, признака дубля и ссылки на созданную запись
  (решение пользователя 2026-10-23, см. «Решения пользователя»). Периоды, ключи активностей и тегов хранятся реляционно (дочерние таблицы), а не в `jsonb`: так остаются возможными фильтры по периоду и активности источника и будущая дедупликация.
- **Соответствие источника Freem живёт рядом с источником.** Найденные в файле активности и теги сохраняются как `ImportDocumentActivity`/`ImportDocumentTag` (ключ источника, название, цвет, статус, ключи тегов),
  в них же хранится решение пользователя: связать с существующей активностью/тегом Freem или создать новую. Отдельной таблицы соответствия нет, потому что у каждого ключа источника ровно одно решение.
- **Статусы.** Только у документа: `Created → Parsing → Parsed`, `Parsing → Failed` при сбое разбора (строки удаляются). У строк статуса нет: «импортирована ли строка» определится позже по записям, которые будут ссылаться на строку.
  Правила переходов описаны в самом статусе (`CanChangeTo`), переход — атомарный метод репозитория (`ExecuteUpdateAsync` с условием по текущему статусу), а не `Update` целой сущности.
- **Репозиторий и модель хранения.** Один `IImportDocumentRepository` на агрегат, как у остальных сущностей (решение пользователя 2026-10-23): документ (создание, удаление, поиск по id и по пользователю, переход статуса), источник (добавление, правка соответствий) и строки (пакетная вставка, постраничное чтение всех строк документа). Таблицы с каскадом от пользователя и от документа. Одна миграция.
- **События.** На этом этапе не вводятся (решение пользователя 2026-10-23): `EntityType` и `EventTypes` не меняются, вопрос возвращается на этапе 4.
- **Срок жизни.** Импорт удаляется только явно пользователем (метод репозитория удаляет импорт вместе со строками каскадом) и вместе с пользователем; автоочистки по возрасту нет (решение пользователя 2026-10-23).

## Решения пользователя (2026-10-23)

- Периоды, ключи активностей и тегов строки хранятся в отдельных таблицах, не в `jsonb`.
- События импорта отложены до этапа 4.
- Только явное удаление импорта, без автоочистки.
- Строки импорта неизменяемы и без статуса; признак дубля, фильтры по статусу и активности, отметка строк применёнными и ошибки применения не делаются. Дубли остаются на совести пользователя, дедупликация и ссылка записи на строку (правки `Record`) обсуждаются позже. Статус `Applying` у документа убран.

## План реализации

Команды из `source`. После каждого шага `dotnet build Freem.sln` без ошибок и предупреждений. Стиль по `CLAUDE.md` (блочные тела, вложенность конструирования не глубже одного уровня, без голых строк в моделях). Коммитов нет, пока пользователь не попросит.

1. **Id и value object'ы в `Freem.Domain/Import`.** `ImportDocumentId`, `ImportRowId` (с `Generate`/`Parse`), `ImportFileName`, `ImportDocumentStatus`, решение по соответствию (`ImportActivityResolution`/`ImportTagResolution`: «существующая `ActivityId`/`TagId`» либо «создать новую»). Проверка: сборка; unit-тесты `Parse` в `Freem.Domain.UnitTests`.
2. **Сущности в `Freem.Domain.Entities/Import`.** `ImportDocument`, неизменяемая `ImportRow` (обёртка над `ImportRecord`), найденные в файле активность и тег с решением соответствия. Ошибка конфликта состояния в `DomainErrorCatalog`, матрица допустимых переходов в `CanChangeTo` статуса документа. Проверка: unit-тесты матрицы.
3. **Интерфейс хранилища в `Freem.Domain.Storage`.** `IImportDocumentRepository` (методы документа и методы над строками, см. «Направление решения») и фильтры. Проверка: сборка.
4. **EF-сущности и конфигурации.** Таблицы импортов, строк, периодов строки, ключей активностей и тегов строки, найденных активностей и тегов с их тегами; имена в `EntitiesNames`, `DbSet` в `DatabaseContext`, каскады от пользователя и от импорта, индексы под фильтры. Проверка: сборка; тесты конфигураций, если они есть для остальных сущностей.
5. **Миграция.** Одна миграция `ImportDocuments`, снимок модели. Проверка: сборка; `Freem.Domain.Storage.PostgreSQL.Migrations.UnitTests`.
6. **`ImportDocumentsRepository`: документ.** Реализация с мапперами; переходы через `ExecuteUpdateAsync` с условием по текущему статусу (ноль строк → ошибка конфликта состояния). Проверка: сборка; интеграционные тесты: создание и чтение, конкурентный второй переход получает ошибку, удаление с каскадом.
7. **`ImportDocumentsRepository`: строки.** Пакетная вставка, постраничное чтение. Проверка: интеграционные тесты: тысячи строк с несколькими периодами, порядок и постраничность, порядок ключей, каскад с документом и пользователем.
8. **Регистрация в DI и финальный прогон.** `dotnet build Freem.sln`, `dotnet test Freem.sln`, `.IntegrationTests` в `docker/test` (docker запускает пользователь). Остановка по шагу 5 `roadmap-stage`: показать результат, записать статус, ждать пользователя.

## Результат реализации

Шаги 1-8 плана выполнены, кроме запуска интеграционных тестов: в сессии агента нет ни PostgreSQL, ни доступа к docker (`permission denied` на сокете), `docker/test` запускает пользователь. Расхождения с планом:

- **Переходы статуса не методы сущности.** `ImportDocument` и `ImportRow` неизменяемы; допустимые переходы описаны в `ImportDocumentStatus.CanChangeTo` (`Freem.Domain/Import`; `Created → Parsing`, `Parsing → Parsed/Failed`), а менять статус можно только атомарным методом репозитория. Так правило перехода живёт в одном месте, а не дублируется между сущностью и репозиторием.
- **Строки без статуса (решение пользователя 2026-10-23).** После ревью этапа убраны статус строки, признак дубля, ссылка на созданную запись, ошибка применения, `MarkRow*`, подсчёты по статусам, фильтры строк, статус документа `Applying`; в плане этапа они были. Остаётся постраничное чтение строк документа.
- **Ошибка перехода.** Новая `import:invalid_status` (`DomainErrorCatalog.Types.ImportInvalidStatus`, в API-маппере 409); неизвестный документ даёт `entity_not_found`. В каталог добавлены `ImportDocumentId`/`ImportRowId` (свойства ошибок, имена сущностей `import_document`/`import_row`).
- **Состав интерфейса `IImportDocumentRepository`:** документ (`Create`, `Delete`, `FindById`, `FindByMultipleId`, `Find` по пользователю, `ChangeStatus`), источник (`AddSource`, `SetActivityResolution`, `SetTagResolution`), строки (`AddRows`, `FindRowById`, `FindRows` по `ImportRowByDocumentFilter`). Порядок строк: начало первого периода, затем id (для этого в строке хранится `first_start_at`).
- **Хранение.** Восемь таблиц: `import_documents`, `import_document_tags`, `import_document_activities`, `import_document_activity_tags`, `import_rows`, `import_row_periods`, `import_row_activities`, `import_row_tags`. Статус документа хранится строкой с проверочным ограничением. Решение соответствия: колонки `create_new` и `resolved_*_id` (внешний ключ на активность или тег с `ON DELETE SET NULL`, то есть при удалении выбранной сущности Freem решение сбрасывается в «не принято»). Ключи активностей и тегов строки хранят позицию (`position`), порядок при чтении сохраняется; ключи тегов внутри активности документа и сами активности и теги документа читаются в порядке ключа источника (множества, порядок не значим). Миграция `20261023033300_ImportDocuments`.
- **Инвариант `ImportRow`:** запись строки обязана иметь хотя бы один период (иначе нечем упорядочить).
- Сущности источника в документе названы `ImportDocumentTag`/`ImportDocumentActivity` (обёртка над `ImportTag`/`ImportActivity` плюс решение).
- **Не проверено:** интеграционные тесты `ImportDocumentsRepositoryTests` (19 тестов: создание и чтение, переходы, конкурентный переход на двух соединениях, источник и решения, сброс решения при удалении активности, порядок ключей строки, 1500 строк с постраничностью, каскады) только собираются. Транслируемость запросов (`ExecuteUpdate` с `SetProperty(..., (string?)null)`, загрузка с `Include` по строкам и документам) и миграция на реальной БД не проверены.
- **Для этапа 4 (замечание независимой проверки):** методы `Set*Resolution` репозитория не проверяют владельца документа и его статус, а `resolved_*_id` не проверяется на принадлежность пользователю; эти проверки делает use case. `AddRowsAsync` не проверяет, что все строки одного документа (в контексте ошибки берётся первая).

Проверено: `dotnet build Freem.sln` без ошибок (3 предупреждения о null в чужих интеграционных тестах, не связанных с этапом); unit-тесты проходят (`Freem.Domain.UnitTests` 276, `Freem.Domain.UseCases.UnitTests` 36, `Freem.Time.UnitTests` 122, `Freem.Domain.Storage.PostgreSQL.UnitTests` 66, `Freem.Domain.Storage.PostgreSQL.Migrations.UnitTests` 4).
