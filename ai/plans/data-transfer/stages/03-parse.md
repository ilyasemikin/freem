# Этап: загрузка и разбор

Автор: Claude Code, claude-sonnet-5-5, 2026-10-23

См. общий контекст и место этого этапа: `ai/plans/data-transfer/general/roadmap.md` (этап 3).

## Зачем именно так

Этап превращает файл пользователя в сохранённый `ImportDocument` со строками, на которых строятся применение (этап 4) и интерфейс (этап 5). Хранилище и модели уже есть (этапы 1-2), поэтому здесь нужны: парсер Time Tracker, изменение
контракта парсера (формату Time Tracker нужен часовой пояс), use case загрузки и API для работы с импортами. Дубли и фильтры сознательно не делаются (решение пользователя 2026-10-23): список показывает все строки.

## Зафиксированные факты

Проверено чтением кода (`source`) и разбором образца `ai/plans/data-transfer/samples/All_21 Oct Wed.csv` (47 строк):

- `IImportParser.ParseAsync(Stream, CancellationToken)` возвращает `ImportParseResult` (теги, активности, записи с ключами источника); реестр `ImportParserRegistry` ищет парсер по `FormatKey`, зарегистрирован пока только `NativeJsonImportParser`
  (ошибки файла возвращает как `Error`, предупреждений у результата нет). Часового пояса в сигнатуре нет.
- Образец: заголовок `ID, Time item ID, Start Date, Start Time, End Date, End Time,  Duration, ...` (пробелы после запятых), 13 колонок, запятых внутри заметок нет, пустая заметка приходит как пробел (26 из 47), `Activity ID` + `Activity Name`
  дают 5 активностей без противоречий имён, повторяющихся `ID` нет, записей с концом не позже начала нет, самая длинная заметка 14 символов. Реальная история с 2020 года образцом не охвачена: запись короче минуты даст начало равное концу.
- `DateTimePeriod` и строка импорта допускают равные начало и конец; нативный парсер отвергает неположительную длительность, а запись `Record` с такой длительностью создать нельзя (это обозначится при применении, этап 4).
- `RecordName` и `ActivityName` ограничены 128 символами, `ActivityName` не пустой; `TimeZoneOffset` с точностью до минуты.
- Use case'ы получают настройки пользователя через `_mediator.GetUserSettingsAsync` (`TimeZoneOffset` по умолчанию `Default`), запись нескольких агрегатов делается в `StorageTransactionRunner.RunAsync` (образец: `CreateRecordUseCase`).
- В API нет ни одной загрузки файла (`IFormFile`/multipart); для экспорта есть контроллер и `DataTransferClient` в клиенте, тонкие контроллеры над API-медиатором.
- Репозиторий этапа 2 даёт: `CreateAsync` документа, `AddSourceAsync`, `AddRowsAsync` (пакетная вставка), `FindRowsAsync` (постранично), `FindAsync` по пользователю, `FindByMultipleIdAsync` (с проверкой владельца), `DeleteAsync` (каскадом со строками).

## Один-два иллюстративных примера (не исчерпывающий список!)

- Строка Time Tracker: `10387, 10349, 1 Oct 2026, 05:29, 1 Oct 2026, 07:29,  01:59:41, 7181471, 2, Work, Sample note 1, , ` → строка импорта с ключом `10387`, активностью-ключом `2`, названием записи `Sample note 1` и периодом
  05:29-07:29 в часовом поясе, указанном при загрузке; разбор «10 полей слева, 2 справа, середина — заметка» делает запятую в заметке безопасной.
- Загрузка нативного JSON, полученного экспортом: теги, активности и записи документа совпадают с исходными (проверка цепочки туда и обратно, обещанная roadmap).

## Направление решения (не пошаговая реализация)

Согласовано пользователем 2026-10-23 (см. «Решения пользователя»):

- **Контракт парсера.** `ParseAsync` получает параметры разбора (минимум часовой пояс файла). Нативный JSON их игнорирует (смещения берёт из файла). Результат разбора получает число строк файла и список предупреждений (номер строки файла + сообщение)
  для строк, которые пропущены или изменены (например, обрезанная заметка), но файл в целом разобран; фатальные ошибки (неузнанный заголовок, битый JSON) остаются `Error`.
- **Парсер Time Tracker** (`FormatKey` `time-tracker`, `csv`, `text/csv`): проверка заголовка, разбор «10 слева + 2 справа», дата `d MMM yyyy` и время `HH:mm` в инвариантной культуре, строки с LF и CRLF, возможный BOM. Заметка → название записи
  (пустая → без названия, длиннее 128 символов → обрезается с предупреждением; запись с началом, равным концу, сохраняется как есть), категории отбрасываются, цвет активности не заполняется (при создании активности выберет этап 4), теги не создаются. Один фиксированный часовой пояс на весь файл (так устроен и `TimeZoneOffset` пользователя).
- **Use case загрузки.** Читает настройки пользователя (часовой пояс по умолчанию), находит парсер, разбирает файл целиком в памяти и в одной транзакции создаёт `ImportDocument`, источник (активности и теги без решений соответствия) и строки порциями.
  В документе сохраняются число строк файла и число разобранных строк. Из-за транзакции документ сразу создаётся в статусе `Parsed`; статусы `Created`/`Parsing`/`Failed` и `ChangeStatus` остаются заделом на фоновый разбор. Файл не хранится. Решения соответствия на этом этапе не предлагаются.
- **API.** Загрузка файла (multipart: формат, часовой пояс необязателен, файл) с ограничением размера, список импортов пользователя, один импорт (с найденными активностями и тегами), постраничный список строк, удаление импорта; `DataTransferClient`
  получает соответствующие методы. Ответ загрузки несёт созданный импорт (с числами строк) и предупреждения; сами предупреждения не сохраняются, остаётся разница «строк в файле» минус «разобрано».

## Решения пользователя (2026-10-23)

1. Запись Time Tracker с началом, равным концу, сохраняется как есть: для импорта это допустимо, при попытке создать из неё запись это будет явно обозначено позже (этап 4).
2. Заметка длиннее 128 символов обрезается (с предупреждением).
3. В сам импорт сохраняются число строк в поступившем файле и число разобранных строк; тексты предупреждений не сохраняются.
4. Документ при загрузке создаётся сразу в статусе `Parsed`.
5. Эндпоинты работы с импортами (список, один импорт, строки, удаление) делаются в этом этапе.

## План реализации

Команды из `source`. После каждого шага `dotnet build Freem.sln` без ошибок и предупреждений в затронутых проектах. Стиль по `CLAUDE.md` (блочные тела, вложенность конструирования не глубже одного уровня, без голых строк в моделях). Коммитов нет, пока пользователь не попросит.

Проверка: сборка; обновлённые unit-тесты нативного парсера.
2. **Числа строк в документе.** `ImportDocument` получает число строк файла и число разобранных (инвариант: разобранных не больше строк файла, оба неотрицательные); колонки, конфигурация, новая миграция `ImportDocumentRowCounts` (миграция этапа 2 закоммичена, существующую не правим), маппер. Проверка: сборка; `Freem.Domain.Storage.PostgreSQL.Migrations.UnitTests`; unit-тесты инварианта; обновление интеграционных тестов репозитория (чтение и запись чисел).
3. **Парсер Time Tracker.** `FormatDescription` (`time-tracker`, `csv`, `text/csv`), разбор по правилам из «Направления решения», регистрация в DI, образец копируется в ресурсы тестового проекта. Проверка: unit-тесты по критерию готовности; тест полноты реестра зелёный.
4. **Use case'ы импортов.** Контракты (`RequestTypes`, запросы и ответы) и обработчики в `Freem.Domain.UseCases/Import`: загрузка (парсер из реестра, часовой пояс из запроса или настроек, одна транзакция: документ в статусе `Parsed`, источник, строки порциями), список, один импорт, постраничные строки, удаление; доступ только к своим импортам. Проверка: сборка; unit-тесты порционной вставки и сопоставления результата разбора со строками там, где они выносятся в отдельный класс; интеграционные тесты в `Freem.Domain.UseCases.IntegrationTests` по критерию готовности.
5. **API.** DTO в `Freem.Api.Public.Contracts`, контракты и обработчики в `Freem.Api.Public.UseCases(.Contracts)`, `ImportsController` в `Freem.Api.Public/Controllers/V1` (multipart-загрузка с ограничением размера, список, один импорт, строки, удаление), OpenAPI. 6. **Клиент.** Методы в `Freem.Api.Public.Client` (загрузка файла, список, получение, строки, удаление), используются тестами API. Проверка: сборка.

## Результат реализации

Шаги 1-7 плана выполнены, кроме запуска интеграционных тестов: в сессии агента нет PostgreSQL, EgoHub и доступа к docker, `docker/test` запускает пользователь. Расхождения с планом и принятые при реализации решения:

- **Контракт парсера.** `ImportParseOptions` (часовой пояс) в `Freem.Domain.UseCases/Import`; `ImportParseResult` получил `RowsInFile` и `Warnings` (`ImportParseWarning`: номер строки файла и `ErrorMessage`, в `Freem.Domain.Entities/Import`); инвариант: число строк файла не меньше числа записей.
- **Числа строк в документе.** `ImportDocument.RowsInFile`/`RowsParsed` (колонки `rows_in_file`, `rows_parsed`, проверочное ограничение `rows_parsed >= 0 AND rows_parsed <= rows_in_file`); новая миграция `20261023040222_ImportDocumentRowCounts` (в ней же ослаблено ограничение `import_row_periods` с `start_at < end_at` до `start_at <= end_at`, см. ниже), миграция этапа 2 не правилась.
- **Парсер Time Tracker** (`TimeTrackerImportParser`, формат `time-tracker`, имя "Time Tracker (CSV)"): UTF-8 с возможным BOM, LF и CRLF, заголовок сверяется с ожидаемыми 13 колонками (иначе `invalid_request`), запятая в заметке сохраняется ("10 полей слева, 2 справа"). Пропускаются с предупреждением (строка считается в `RowsInFile`, но не в `RowsParsed`): слишком мало колонок, нет или повторяется `ID`, неразбираемая дата или время, конец раньше начала, нет `Activity ID`, пустое или длиннее 128 символов название активности. Начало, равное концу, сохраняется; заметка длиннее 128 символов обрезается с предупреждением. Разное название у одного `Activity ID` оставляет первое с предупреждением. Пустые строки файла игнорируются и не считаются.
- **Use case'ы** (`Freem.Domain.UseCases/Import`): `UploadImportUseCase` (часовой пояс из запроса или настроек пользователя; разбор в памяти до транзакции, затем документ в статусе `Parsed` и строки порциями по 500 в одной транзакции; ошибка формата или файла не оставляет документа), `GetImportUseCase`, `ListImportUseCase`, `ListImportRowUseCase`, `RemoveImportUseCase`; доступ только к своим импортам через `FindByMultipleIdAsync`. Сопоставление результата разбора с документом и строками вынесено в публичный `ImportDocumentFactory`. Статусы `Created`/`Parsing`/`Failed` и `ChangeStatusAsync` остаются без потребителей (заделом).
- **API** (`/api/v1/imports`): `POST` multipart (поля `format`, необязательный `timeZoneOffset`, файл `file`; `201` с импортом и предупреждениями), `GET` список (с заголовками количества), `GET {id}`, `GET {id}/rows` (с заголовками количества), `DELETE {id}`. Лимит файла 32 МиБ (`ImportsController.MaxFileSize`), поля формы разбираются в API-обработчике, неверные значения дают `invalid_request` (400). Для JSON добавлены конвертеры `ImportDocumentId`, `ImportRowId`, `ImportFileName`, `ImportDocumentStatus`; для списков добавлены привязчики запросов по образцу записей.
- **Клиент:** `ImportsClient` (`UploadAsync`, `ListAsync`, `GetAsync`, `ListRowsAsync`, `RemoveAsync`) и собственный `ImportFormContent` (multipart с текстовыми полями и файлом, потому что `MultipartFormDataFilesContent` из `Utilities.Http` умеет только файлы); `CompositeClient.Imports`.
- **Тесты:** unit: парсер Time Tracker (12 тестов, образец целиком), фабрика документа, инвариант документа, нативный парсер на новый контракт; интеграционные: `ImportUseCasesTests` (10, `Freem.Domain.UseCases.IntegrationTests`), `ImportTests` (9, `Freem.Api.Public.IntegrationTests`), `ImportDocumentsRepositoryTests` обновлён под числа строк. Образец скопирован в `Freem.Domain.UseCases.UnitTests/Resources/TimeTrackerSample.csv` и подключается ссылкой в оба интеграционных проекта.
- **Проверка на запущенном API.** По просьбе пользователя API запущен локально (`dotnet run`, порт 10190) на dev-базе `freem`; миграции этапов 2-3 применены к ней командой `dotnet ef database update` (раньше они там не применялись). Проверено `curl`'ом: загрузка образца (201, 47/47, 5 активностей, смещение 03:00 переведено в UTC), `GET` импорта, постраничные строки и список с заголовками количества, загрузка экспорта нативного JSON (3/3, 3 активности), файл с предупреждениями (пропущена строка с неверной датой, заметка обрезана до 128, начало равное концу сохранено), 404 на неизвестный формат и импорт, 400 на неверный ключ формата, смещение, отсутствие файла или формата, битый файл и слишком большой файл (32 МиБ; ответ 400, а не 413), 401 без токена, 415 на JSON вместо multipart, 404 при обращении другого пользователя (получение, строки, удаление), удаление и отсутствие остатков после неудачных загрузок. DI с `ValidateOnBuild` и OpenAPI (`/api/v1/imports`, `{importId}`, `{importId}/rows`) подтверждены стартом API.
- **Найденная ошибка.** Загрузка с предупреждениями отвечала 500: ограничение `import_row_periods_start_at_end_at_check` (`start_at < end_at`, скопировано у записей) отвергало строку с началом, равным концу, а по решению пользователя такие строки сохраняются. Исправлено ограничением `start_at <= end_at` (миграция `ImportDocumentRowCounts` пересоздана, на dev-базе откатана и применена заново) и тестом репозитория `AddRowsAsync_ShouldSaveRow_WhenPeriodStartEqualsEnd`.
- **Не проверено:** интеграционные тесты в `docker/test` не запускались, они только собираются; не проверен веб-интерфейс (его в этапе нет); ответ `400` вместо `413` на слишком большой файл принят как есть. Один фиксированный часовой пояс на весь файл (так устроен `TimeZoneOffset` пользователя).
- **Известные ограничения (замечания независимой проверки, правок кода нет).** Даты читаются в инвариантной культуре: файл с неанглийскими названиями месяцев даст предупреждения «неверная дата» на каждой строке, а не ошибку формата. Кавычки CSV не поддержаны: запятая допустима только в заметке (схема «10 слева, 2 справа»), запятая в названии активности сломает разбор строки. Имя файла с разделителем `\` на Linux (`C:\x.csv`) отвергается как неверное (400). Лимита на число или объём импортов пользователя нет.

Проверено: `dotnet build Freem.sln` без ошибок (при полной пересборке 8 предупреждений о null, все в ранее существовавших тестах событий, не связанных с этапом); unit-тесты проходят (`Freem.Domain.UnitTests` 282, `Freem.Domain.UseCases.UnitTests` 54, `Freem.Time.UnitTests` 122, `Freem.Domain.Storage.PostgreSQL.UnitTests` 66, `Freem.Domain.Storage.PostgreSQL.Migrations.UnitTests` 4).
