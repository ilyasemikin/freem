## Зачем именно так

Бэкенд этапов 1-4 закрыт, но пользоваться им можно только через `curl`. Этап даёт интерфейс под целевой сценарий пользователя: загрузил файл → один раз сопоставил активности и теги
с существующими → сохраняешь выбранные строки (все сразу или отмеченные) → видишь результат. Плюс скачивание экспорта. Интерфейс строится поверх готового API без изменения его контрактов;
в бэкенде меняется только политика CORS (имя файла экспорта, см. «Решения пользователя»). Логика (проверки сопоставления, предел строк, пропуск нулевой длительности) остаётся на сервере; фронтенд показывает
её результат, а не дублирует.

## Зафиксированные факты

Проверено чтением кода (`source`) и запуском `npm run build`/`npm run lint`:

- **Состояние фронтенда.** `npm run build` проходит (только предупреждение Vite о размере чанка больше 500 кБ), `npm run lint` без замечаний. Интерфейс на английском. Маршруты в `src/app/router.tsx`:
  `/` (`Dashboard`: активности слева, справа вкладки Tags/Records/Statistics), `/activities`, `/records`, `/records/statistics`, `/tags`, `/settings`. В `/settings` попадают из меню пользователя
  в `AppHeader` (кнопка `pi-user` → `OverlayPanel` с Settings и Log out). Страница настроек — образец отдельной страницы: `AppHeader` + `DashboardPanel` + `PanelHeader`, кнопка Back на `/`.
- **Клиент API.** `HttpClient` (`src/clients/http`) всегда сериализует `body` в JSON с `Content-Type: application/json`; отправки `FormData` (multipart) и чтения ответа как файла нет. При 401 один раз
  обновляет сессию и повторяет запрос. Клиенты по сущностям (`ActivitiesClient` и т.д.) возвращают сырой `Response`, регистрируются в `BackendClientsProvider`/`IBackendClientsContext`.
- **Ошибки.** Страницы показывают `response.statusText` через `ValidationError`; тело `ErrorResponse` (`{ error: { code, … } }`) нигде не разбирается. Для применения импорта код ошибки важен
  (`import:unmapped_entities` с ключами в деталях, `import:too_many_rows`).
- **Постраничность.** `ListResponse<T>` (`items`, `count`, `totalCount`) объявлен, но не используется; заголовки `X-ITEMS-COUNT`/`X-TOTAL-ITEMS-COUNT` нигде не читаются. На сервере CORS их
  открывает (`WithExposedHeaders` в `Program.cs`), верхнего предела `limit` у списков импорта нет (только `> 0`), по умолчанию 100. `DataTable`/`Paginator`/`FileUpload` PrimeReact в коде не используются.
- **Кеши.** `src/cache` — кеши активностей и тегов по id (`EntitiesCache`, без инвалидации), записи и статистика читаются без кеша. `ActivitiesEntitiesCache.findByNameRequest` и `ActivitiesPicker`
  (`AutoComplete` с поиском по имени через `api/v1/activities/by-name`) — готовый способ выбрать существующую активность; для тегов так же `TagsPicker`. Данные импорта кешировать незачем: они
  принадлежат одному импорту и нужны только на его странице.
- **Обновление записей.** `Dashboard` перерисовывает записи и статистику по локальному счётчику `recordsVersion`; при переходе на `/` страница монтируется заново и читает данные с сервера.
- **Часовой пояс.** `TimeZoneOffset` (`src/data`) с `toString()` в формате API (`03:00:00`), списком `all()` и `fromBrowser()`; настройка пользователя в `useUserSettings()`. Выбор пояса уже сделан
  в `SettingsPage` (`Dropdown` + кнопка «As in browser»).
- **Форматы.** `GET api/v1/formats` возвращает `{ exportFormats[], importFormats[] }`, у формата `key`, `name`, `fileExtension`, `mediaType`. Признака «формату нужен часовой пояс» нет; пояс нужен только
  `time-tracker`, `freem-json` берёт смещения из файла.
- **Загрузка.** `POST api/v1/imports`, multipart: `format`, `timeZoneOffset` (строка вида `03:00:00`, необязательно), `file`; предел 32 МиБ (`ImportsController.MaxFileSize`). Ответ 201
  `{ import, warnings[] }`, предупреждение — `{ lineNumber, message }`; предупреждения не сохраняются, после загрузки остаётся только разница `rowsInFile - rowsParsed`.
- **Экспорт.** `GET api/v1/export/{format}` отдаёт файл потоком с `Content-Disposition: attachment; filename=freem-export-<время>.<расширение>`, но `Content-Disposition` не входит в открытые CORS
  заголовки, поэтому фронтенд с другого origin (`npm run dev` на 10191, API на 10190) имени файла не прочитает. Токен передаётся только заголовком `Authorization`, поэтому обычная ссылка
  `<a href>` не сработает: файл нужно получать через `fetch` и отдавать браузеру из `Blob`.
- **Поиск активностей по имени.** `GET api/v1/activities/by-name` (`FindActivityUseCase`, `ActivityFilter`) фильтрует только по пользователю и вхождению текста в имя (с учётом регистра), до размера
  страницы по умолчанию; статус не фильтруется, архивные активности в ответ попадают. Поле `status` в `ActivityResponse` фронтенда есть.
- **Сопоставление и применение** — как в «Что уже есть» этапа 4: `PUT …/activities/{importActivityId}` `{ activityId }`, `PUT …/tags/{importTagId}` `{ tagId }` (null снимает), `POST …/apply` с ровно
  одним из `{ all: true }`/`{ rowIds }`, ответ `{ recordsCreated, skippedRowIds }`, ошибки 422/400/409. Выбора «все, кроме отмеченных» API не поддерживает.

## Один-два иллюстративных примера (не исчерпывающий список!)

- Пользователь выбирает формат Time Tracker, пояс по умолчанию из настроек, файл с историей с 2020 года (~десятки тысяч строк). Получает страницу импорта: 5 активностей файла, у каждой выбор
  существующей активности; таблица строк по 100 на странице с общим числом. Сопоставляет 5 активностей, нажимает «сохранить все строки» → `{ all: true }` → видит «создано N записей, пропущено M строк».
- Пользователь отмечает на первой и третьей страницах по несколько строк, отметки сохраняются при листании, «сохранить выбранные (7)» → `{ rowIds: [...] }`. Если какая-то активность не
  сопоставлена, сервер отвечает `import:unmapped_entities`, и интерфейс подсвечивает именно эти активности.

## Направление решения (не пошаговая реализация)

- **Страницы** (имена по сущностям API). В меню пользователя рядом с Settings два пункта: Imports и Export.
  - `/imports` — загрузка нового файла и список прежних импортов с удалением.
  - `/imports/:id` — один импорт: сводка (файл, формат, пояс, строк в файле/разобрано), сопоставление активностей и тегов, таблица строк, кнопки применения и результат.
  - `/export` — выбор формата и скачивание.
- **Загрузка.** Формат, часовой пояс (поле показывается всегда, по умолчанию пояс из настроек пользователя; для `freem-json` сервер его игнорирует), файл. После ответа — переход на страницу импорта
  с предупреждениями разбора.
- **Клиент.** `DataTransferClient` (форматы, экспорт) и `ImportsClient` (все эндпоинты импортов) в стиле существующих клиентов. `HttpClient` получает отправку `FormData` (без JSON и без своего
  `Content-Type`) — минимальное расширение, без нового слоя. Модели запросов и ответов в `src/clients/models/...` по образцу существующих. Чтение заголовков количества в `ListResponse`.
  Разбор `ErrorResponse` (код и детали) — для страниц импорта.
- **Сопоставление.** Для каждой активности файла — выбор одной существующей активности поиском по имени (по образцу `ActivitiesPicker`, но одиночный выбор), сохранение сразу `PUT` при выборе,
  снятие — очистка. Архивные активности не предлагаются: отсекаются на фронтенде по `status`, поиск на сервере не меняется. Теги так же; блок тегов показывается, только если в файле есть теги. Активности и теги файла читаются постранично, как отдаёт API.
- **Строки.** Таблица с постраничностью на сервере (`offset`/`limit`, общее число из заголовка): название, описание, активности файла (с подписью сопоставленной), периоды во времени пользователя.
  Выбор — отметки строк, накапливаются по id между страницами. Два независимых действия: «сохранить все строки» (`{ all: true }`, без перечисления id) и «сохранить отмеченные (N)»
  (`{ rowIds }`); режима «все, кроме отмеченных» нет.
- **Применение и результат.** Применяется сразу, без подтверждения: повторное применение создаёт дубли, это допустимо. После ответа: число созданных записей и пропущенные строки (их id
  сопоставляются со строками таблицы, если они на текущей странице; иначе показывается число). Ошибки 422/400/409 показываются по коду ошибки, а не `statusText`.
- **Экспорт.** `fetch` с токеном → `Blob` → временная ссылка с `download`. Имя файла берётся из `Content-Disposition` ответа. Для этого бэкенд добавляет `Content-Disposition` в
  `WithExposedHeaders` политики CORS в `Program.cs`. Это стандартный механизм CORS (`Access-Control-Expose-Headers`): клиент читает заголовок обычным `response.headers.get(...)` без
  дополнительных настроек. Нужен и для `npm run dev` (10191 → 10190), и для `docker/service` (web 10171 → API 10170): там тоже разные origin.

3. **Клиенты и модели.** `DataTransferClient` (форматы, экспорт) и `ImportsClient` (загрузка, список, импорт, активности, теги, строки, сопоставления, применение, удаление), модели запросов

8. **Проверка на develop.** Свой API (`dotnet run`, 10190) на `docker/develop`, `npm run dev` (10191); сценарий по критерию готовности запросами к API (включая заголовок CORS); браузерный проход —
