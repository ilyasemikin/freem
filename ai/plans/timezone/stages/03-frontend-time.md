# Этап: время во фронтенде

Автор: Claude Code, claude-opus-5-5, 2026-10-21

См. общий контекст и место этого этапа: `ai/plans/timezone/general/roadmap.md` (этап 3).

## Зачем именно так

После этапов 1-2 сервер считает сутки по `TimeZoneOffset` пользователя, а фронтенд по-прежнему смешивает локальное время браузера и UTC.
Пояс пользователя не обязан совпадать с поясом браузера, поэтому опираться на локальное время `Date` нельзя. Нужен один слой
преобразований «момент UTC ↔ время на часах пользователя», через который проходят показ, ввод и границы суток. Без него каждая
страница будет снова решать вопрос по-своему.

## Зафиксированные факты

- Показ времени: `DateHelper.toFormattedString` (`src/helpers/DateHelper.ts`) — `toISOString().slice(11, 19)`, то есть UTC. Им
  пользуется `RecordPanel` (`formatTime`, диапазон записи и строки периодов). Дат в диапазоне нет: запись через полночь показывается как «17:00 - 08:00».
- Ввод времени: `DatePicker` (`src/components/inputs/DatePicker.tsx`) — обёртка над PrimeReact `Calendar`, работает в локальном времени браузера
  (пропа часового пояса у `Calendar` нет). Используется в `RecordPeriodRow` (начало/конец периода) и `RunningRecordEditor` (начало, `maxValue={now}`).
- Границы суток: `DateHelper.getPeriod(unit, date)` считает начало дня/месяца/года по локальному времени браузера (`setHours(0, 0, 0, 0)`),
  затем `DatePeriod` обрезает время через `Date.UTC(getFullYear(), getMonth(), getDate())` и хранит полночь UTC. `DatePeriod.toString()`
  выдаёт даты `YYYY-MM-DD, YYYY-MM-DD`.
- Список записей: `RecordsDashboard` отправляет `ListRecordByPeriodRequest(period.toString())`, то есть даты без времени. Сервер разбирает их
  `DateTimeOffset.TryParse` как полночь по поясу процесса сервера (`DateTimePeriod.TryParse`), а не по поясу пользователя.
- Группировка: `RecordListGrouped` группирует по `record.startAt` в локальных датах браузера (`getDate()`/`getMonth()`).
- Статистика: `StatisticsDashboard` берёт период из `DateHelper.getPeriod`, `DatePeriodHelper.toPerPeriodRequest` отправляет дату дня/месяца/года;
  границы по смещению сервер считает сам (этап 1). При этом `toPerPeriodRequest` читает `period.start.getDate()` локально у значения, которое
  хранит полночь UTC: в браузере с отрицательным поясом это предыдущий день (из кода, запуском не проверено).
- Настройки: `UserClient.getSettings/updateSettings` есть, модели `UserSettingsResponse`/`UpdateUserSettingsRequest` с `timeZoneOffset` (формат
  `"c"`: `03:00:00`, `-05:30:00`). Настройку никто не загружает и не использует, страницы настроек нет. Маршруты — `src/app/router.tsx`,
  основной экран — `Dashboard` с `AppHeader`, в меню пользователя только «Log out».
- Кэш: `EntitiesCacheProvider` кэширует только активности и теги; записи и статистика загружаются заново при изменении зависимостей эффектов.
- Тестов во фронтенде нет (в `package.json` нет тестового раннера); проверки — `npm run build` (`tsc -b` + `vite build`) и `npm run lint`.

## Один-два иллюстративных примера (не исчерпывающий список!)

- Пользователь с `03:00:00`, браузер в UTC: сейчас запись 10:00-11:00 по Москве (07:00-08:00 UTC) показывается как «07:00 - 08:00», а введённое
  в `Calendar` «10:00» сохраняется как 10:00 UTC. После этапа и показ, и ввод — «10:00» по поясу пользователя.
- Список за 21.10 при `03:00:00` запрашивает `2026-10-20T21:00:00.000Z, 2026-10-21T21:00:00.000Z`, а запись 20.10 22:00 - 21.10 01:00 показывается как
  «22:00 - 01:00 21/10».

## Направление решения (не пошаговая реализация)

- Настройка: контекст (провайдер) с текущим `TimeZoneOffset`, который загружается после входа и обновляется после сохранения на странице
  настроек. Компоненты, зависящие от пояса, берут его из контекста; при смене смещения эффекты загрузки списков и статистики перезапускаются.
- Один хелпер пояса: разбор/формат `"c"`, перевод момента в «время на часах пользователя» и обратно, начало суток/месяца/года по дате пользователя,
  «сегодня» по поясу пользователя. Для `Calendar` — представление времени пользователя как `Date` с такими же локальными полями и обратное
  преобразование (стандартный приём для компонентов без поддержки пояса).
- Показ: формат времени и дат записей через хелпер; диапазон записи показывает дату у конца, если конец в другие сутки пользователя.
- Списки: границы суток для `by-period` считает фронтенд по смещению и отправляет точными моментами (ISO с `Z`); группировка — по дате начала у пользователя.
- Статистика: дата дня/месяца/года берётся по поясу пользователя (заодно уходит ошибка с `getDate()` в отрицательном поясе браузера).
- Страница настроек: отдельный маршрут, ссылка в меню пользователя `AppHeader`, выбор смещения и сохранение через `updateSettings`.

Решения пользователя (2026-10-21):

1. Смещение выбирается из выпадающего списка от `UTC−12:00` до `UTC+14:00` с шагом 15 минут; кнопка «Как в браузере» подставляет смещение браузера.
2. Страница — маршрут `/settings`, пункт «Settings» в меню пользователя над «Log out».
3. `vitest` не добавляется; проверка — сборка, lint и ручная проверка в браузере силами агента.
4. Сдвиг значений `Calendar` при переводе часов в поясе браузера (DST) — допустимое ограничение, отдельно не обрабатывается.

## Явно не входит в этот файл (пока)

- Показ по смещению из периода записи (решение пользователя: всё по текущей настройке).
- Переработка интерфейса страниц сверх нужного для времени (отдельная задача в `tasks.md`).

## Критерий готовности

- `npm run build` и `npm run lint` в `Freem.Web` без ошибок.
- Ручная проверка в браузере (по решению пользователя её делает агент): при смещении, отличном от пояса
  браузера, введённое время сохраняется и показывается одинаково; список и группировка по дням идут по суткам пользователя; запись через
  полночь показывает дату у конца; смена смещения на странице настроек сразу меняет показ и границы суток.
- Бэкенд на этом этапе не меняется (если понадобится — запись в «Статус и изменения»).

## План реализации

1. Модель смещения (`"c"` ↔ минуты, показ `UTC+03:00`, смещение браузера, список значений) и хелпер пояса: момент ↔ время на часах
   пользователя, значение для `Calendar` и обратно, «сегодня», начало суток. Даты без времени (`DatePeriod`, `DateHelper.getPeriod`,
   `DatePeriodHelper`) считаются по UTC-полям, без локального времени браузера. Проверка: `npm run build`.
2. Контекст настройки: загрузка после входа, обновление после сохранения, хук для компонентов. Проверка: `npm run build`.
3. Показ и ввод: `DatePicker` принимает и отдаёт моменты, внутри переводит в пояс пользователя; формат времени в `RecordPanel`, дата у
   конца на другом дне; группировка `RecordListGrouped` по дате пользователя. Проверка: `npm run build`, `npm run lint`.
4. Границы суток: выбор периода от «сегодня» пользователя, `by-period` точными моментами, запрос статистики по UTC-полям даты.
   Проверка: `npm run build`, `npm run lint`.
5. Страница `/settings` и пункт меню. Проверка: `npm run build`, `npm run lint`, затем ручная проверка в браузере.
