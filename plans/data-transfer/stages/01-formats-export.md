# Этап: абстракции форматов и экспорт в JSON

Автор: Claude Code, claude-sonnet-5-5, 2026-10-21

См. общий контекст и место этого этапа: `plans/data-transfer/general/roadmap.md` (этап 1).

## Зачем именно так

Формат должен добавляться без правок ядра, а нативный JSON должен и писаться, и читаться (этапы 3-4 используют ту же схему на чтение). Поэтому сначала модель экспорта и реестр
форматов, а экспорт нативного JSON служит первым потребителем и проверкой этих абстракций. Модели импорта и экспорта раздельные: у экспорта есть id Freem, у импорта ссылки принадлежат источнику и результат разбора затем сохраняется строками импорта.

## Зафиксированные факты

Проверено чтением кода (`_Src/Freem`):

- `Record` (`Freem.Domain.Entities/Records/Record.cs`): `Name`, `Description`, `Activities`, `Tags` (коллекции id), `Periods` — каждый `RecordPeriod` имеет `Period` (`DateTimePeriod`),
  `TimeZoneOffset`, `Description`, собственный `RecordPeriodId`. Период с неположительной длительностью запрещён конструктором.
- `Activity`: `Name`, `Color`, `Status` (`Active`/`Archived`), связанные теги. `Tag`: только `Name`.
- Репозитории `IRecordRepository`/`IActivityRepository`/`ITagRepository` отдают `AsyncBatch<T>` через фильтры `...ByUserFilter` с `Limit`/`Offset`; `ListRecordUseCase` показывает паттерн постраничного чтения.
  Потокового чтения всех записей одним вызовом нет.
- Use case'ы: `Freem.Domain.UseCases` (`IRequestHandler<HandlerContext, TRequest, Result<TResponse, Error>>`), контракты в `Freem.Domain.UseCases.Contracts`, типы запросов в `RequestTypes.cs`,
  регистрация в `AddEntitiesUseCases`. API-слой: `Freem.Api.Public.UseCases` (маппинг DTO и ошибок) и тонкие контроллеры в `Freem.Api.Public/Controllers/V1`.
- JSON домена: `Freem.Domain.Serialization.Json` (`EntitiesJsonSerialization.Populate`, snake_case, `ParsableJsonConverter<T>` для value object'ов). Отдельной схемы с версией нет.
- Абстракции «формат» и реестра в проекте нет (план это подтверждает).

## Один-два иллюстративных примера (не исчерпывающий список!)

- Реестр с тестом на полноту: по образцу StashIt — тест, который перебирает все реализации интерфейса формата в сборке и проверяет, что каждая зарегистрирована в DI и имеет уникальный ключ.
- Элемент модели экспорта: запись с id Freem, ссылками на активности и тегами по id, периодами (`Start`, `End`, `TimeZoneOffset`, `Description`); активности и теги отдаются форматам такими же плоскими элементами.

## Направление решения (не пошаговая реализация)

- Отдельный проект не создаётся (решение пользователя 2026-10-21). Модели импорта и экспорта раздельные (решение пользователя 2026-10-21): общей «модели обмена» нет.
  - Экспорт: плоская модель данных для записи, строится из доменных сущностей, несёт id Freem, отдаётся форматам потоком элементов (экспорт не держит всю историю в памяти). Интерфейс `IExportWriter`.
  - Импорт: своя модель результата разбора, ссылки и id принадлежат источнику (ключи файла), а не Freem; форма уточняется на этапах 2-3 вместе с сущностями строк импорта. Интерфейс `IImportParser`
    объявляется здесь, парсеры реализуются на этапе 3.
  - Формат нативного JSON владеет своими DTO файла (с полем `version`, snake_case); маппинг «модель экспорта → DTO» и «DTO → модель импорта» пишется отдельно с каждой стороны.
    Совпадение схемы на чтение и запись проверяется тестом «туда и обратно».
- Расположение (решение пользователя 2026-10-21, уточнено 2026-10-23): в `Freem.Domain` только то, что переиспользуется на всех уровнях (ключ и описание формата: контракты, API, клиент);
  модели экспорта и результата разбора импорта, нужные лишь use case'ам, лежат в `Freem.Domain.Entities` (папки `Export` и `Import`), туда же пойдут сущность импорта и строки импорта этапа 2.
- Понятие «формат» разделено на описание и исполнителя: `IImportParser` (читает `Stream` в результат разбора) и `IExportWriter` (пишет элементы экспорта в `Stream`), каждый знает описание своего формата.
  Это активно действующие объекты, поэтому они, реестр по ключу формата (раздельно для импорта и экспорта, DI, тест на полноту), use case экспорта и маппинг доменных сущностей в модель экспорта
  лежат в `Freem.Domain.UseCases` (папки `Export` и `Import`). Реализация нативного JSON с DTO файла там же: `Freem.Domain.Serialization.Json` ссылается только на `Freem.Domain` и сериализует доменные типы,
  файловой схеме там не место (пересматривает прежнее решение о размещении формата в `Freem.Domain.Serialization.Json`).
- Use case экспорта читает активности, теги и записи пользователя порциями и пишет в `Stream`; эндпоинт отдаёт файл (`Content-Disposition`), плюс эндпоинт списка форматов.
  Экспорт и импорт синхронные, без фоновых задач (решение пользователя).

## Решения пользователя (2026-10-21)

- Экспортируются все сущности: все активности (включая архивные), все теги (даже без записей), все записи.
- Экспорт и импорт синхронные, для начала достаточно.
- В экспорт пишутся id сущностей Freem (записи, активности, теги, периоды). Использование id при повторном импорте (в дополнение к «активность + начало + конец») уточняется на этапах 3-4.

## Форма моделей (решение пользователя 2026-10-21)

- Экспорт: поток элементов (активности, теги, записи), вся история в памяти не держится.
- Импорт: результат разбора целиком, документом (`ImportDocument`): парсер читает файл целиком, а строки сразу сохраняются в БД на этапе 3. Состав документа уточняется на этапах 2-3.

## Явно не входит в этот файл (пока)

Парсеры (этап 3), модель импорта и хранилище (этап 2), применение (этап 4), интерфейс скачивания (этап 5). Структура полей схемы JSON уточняется при реализации.

## Критерий готовности

- `dotnet build Freem.sln` и `dotnet test Freem.sln` проходят; тест полноты реестра и тесты маппинга доменные сущности → модель экспорта → JSON и JSON → модель импорта, плюс тест «туда и обратно».
- `GET` эндпоинта экспорта возвращает валидный JSON со схемой и версией для пользователя с активностями, тегами, записями с несколькими периодами; `GET` списка форматов возвращает нативный JSON.
- Интеграционный тест use case экспорта в `docker/test` на реальном хранилище.

## План реализации

Команды выполняются из `_Src/Freem`. После каждого шага `dotnet build Freem.sln` без ошибок и предупреждений, если не сказано иное. Стиль кода по `CLAUDE.md` (блочные тела методов, вложенность конструирования не глубже одного уровня).
Коммитов нет, пока пользователь не попросит.

1. **Value object'ы в `Freem.Domain`.** Папки `Export` и `Import`: описание формата (ключ, отображаемое имя, расширение, media type), элементы модели экспорта (активность, тег, запись с периодами; id Freem, ссылки по id),
   пустой каркас `ImportDocument`. Ключ формата — value object с `Parse`, бросающим `FormatException`. Проверка: сборка; unit-тесты на `Parse` ключа и инварианты описания в `Freem.Domain.UnitTests`.
2. **Интерфейсы и реестр в `Freem.Domain.UseCases`.** `IExportWriter` (описание формата, запись `IAsyncEnumerable` элементов в `Stream`), `IImportParser` (описание формата, чтение `Stream` в `ImportDocument`),
   реестры по ключу отдельно для экспорта и импорта (ошибка «формат не найден» в `DomainErrorCatalog`), регистрация в DI. Проверка: сборка; unit-тест реестра на поиск по ключу и на дубликаты ключей.
3. **Тест полноты реестра.** Перебирает все реализации `IExportWriter`/`IImportParser` в сборке и проверяет регистрацию в DI и уникальность ключей (образец — StashIt). Проверка: тест зелёный, а при добавлении незарегистрированной реализации (временно, локально) падает.
4. **Чтение данных пользователя для экспорта.** Сервис в `Freem.Domain.UseCases/Export`, который порциями (`Limit`/`Offset` через `ActivityByUserFilter`, `TagByUserFilter`, `RecordByUserFilter`) отдаёт `IAsyncEnumerable` элементов модели экспорта:
   сначала теги, затем активности, затем записи. Маппинг доменных сущностей в элементы. Проверка: unit-тесты маппинга на записи с несколькими периодами, архивной активностью, тегом без записей.
5. **Нативный JSON: DTO файла и писатель.** В `Freem.Domain.UseCases/Export` (формат владеет DTO): поле `version`, snake_case, потоковая запись через `Utf8JsonWriter`, маппинг «модель экспорта → DTO». Проверка: unit-тест на содержимое файла (golden-строка), на `version`, на порядок разделов.
6. **Нативный JSON: парсер.** Читает тот же файл в `ImportDocument` (DTO → модель импорта); состав `ImportDocument` ровно настолько, насколько нужно тесту «туда и обратно» (уточняется на этапах 2-3). Проверка: тест «туда и обратно»
   (элементы → писатель → парсер → сравнение с исходными данными), тест на неподдерживаемую `version`.
7. **Use case экспорта.** Контракты в `Freem.Domain.UseCases.Contracts` (`RequestTypes`), обработчик `Result<…, Error>`, регистрация в `AddEntitiesUseCases`. Запрос несёт ключ формата и выходной поток; чтобы API успел выставить
   `Content-Type`/`Content-Disposition` до тела ответа, запрос получает фабрику потока, которую use case вызывает с описанием формата после проверки ключа. Проверка: сборка; интеграционный тест в `Freem.Domain.UseCases.IntegrationTests`
   на реальном хранилище (пользователь с активностями, тегами, записями с несколькими периодами; неизвестный ключ формата → ошибка).
8. **Use case списка форматов.** Отдаёт описания зарегистрированных писателей и парсеров (с признаком направления). Проверка: unit-тест.
9. **API.** Контракты в `Freem.Api.Public.UseCases.Contracts`, обработчики в `Freem.Api.Public.UseCases`, контроллер в `Freem.Api.Public/Controllers/V1` (экспорт файлом, список форматов), записи в OpenAPI. Проверка: сборка;
   интеграционные тесты `Freem.Api.Public.IntegrationTests` (заголовки файла, валидный JSON, 401 без токена, 404/422 на неизвестный формат).
10. **Клиент.** Методы в `Freem.Api.Public.Client` для списка форматов и скачивания экспорта (пригодятся тестам и фронтенду этапа 5). Проверка: сборка; используется в интеграционных тестах API.
11. **Финальный прогон.** `dotnet build Freem.sln`, `dotnet test Freem.sln`, `.IntegrationTests` в `docker/test` (`docker compose up --build --abort-on-container-exit test`, затем `down -v`; docker запускает пользователь).
    Остановка по шагу 5 `roadmap-stage`: показать результат, записать статус, ждать пользователя.

- На будущее (пожелание пользователя 2026-10-23): `IExportWriter`/`IImportParser` и их реализации можно будет вынести в отдельные проекты форматов. Сейчас проекты не делятся; чтобы вынос остался дешёвым,
  реализации форматов зависят только от value object'ов `Freem.Domain` и интерфейсов, не от репозиториев, `HandlerContext` и других деталей use case'ов (чтение данных и маппинг остаются в сервисе шага 4).
- Порядок разделов файла (теги, активности, записи) нужен, чтобы читатель мог разрешать ссылки без второго прохода.

## Результат реализации

Шаги 1-11 плана выполнены, кроме запуска интеграционных тестов (им нужны PostgreSQL и EgoHub, `docker/test` запускает пользователь). Расхождения с планом:

- В `Freem.Domain` остались только переиспользуемые на всех уровнях value object'ы формата (`FormatKey`, `FormatName`, `FormatFileExtension`, `FormatMediaType`, `FormatDescription` в `Formats`) и `ImportActivityId`, `ImportTagId`, `ImportRecordId` (`Import`, id из файла); голых строк в моделях и DTO нет (по замечанию пользователя), строки остались только в DTO файла нативного JSON. Модели экспорта и результата разбора (`ExportItem`, `ExportTag`, `ExportActivity`, `ExportRecord`, `ImportDocument` и др.) по замечанию пользователя перенесены в `Freem.Domain.Entities` (папки `Export` и `Import`): они нужны только use case'ам, то есть фактически сущности.
- Для use case'ов не было тестового проекта: добавлен `Freem.Domain.UseCases.UnitTests` (в `Freem.sln`, в папке UseCases). Тест полноты реестра проверяет регистрацию в DI и уникальность ключей;
  проверка «падает при незарегистрированной реализации» вручную не делалась, она следует из сравнения множеств.
- Чтение данных вынесено в `ExportItemReader` (размер порции задаётся конструктором, по умолчанию 500; активности читаются по `Id`, чтобы страницы были устойчивы). Ошибка репозитория посреди потока
  поднимается как `ExportReadException` и в use case превращается в `Error`.
- Писатель нативного JSON пишет `Utf8JsonWriter` напрямую (потоково), DTO файла нужны только парсеру (`Import/NativeJson`); имена свойств общие (`NativeJsonFormat.Properties`). Схема: `format` ("freem"),
  `version` (1), затем `tags`, `activities`, `records`; отсутствующие имя/описание не пишутся.
- `ImportDocument` содержит теги, активности и записи с ключами источника (строки), цвет активности необязателен; парсер проверяет формат, версию, дубли ключей, ссылки и положительную длительность периодов.
- Добавлена ошибка `format:not_found` (404). Неверный ключ формата в маршруте даёт 400 через `FormatException`. Для JSON домена добавлен конвертер `FormatKey`.
- Заголовки файла выставляет контроллер в фабрике потока, переданной в use case. Если чтение падает после начала ответа, соединение обрывается (`HttpContext.Abort`), а не отдаётся «валидный» файл.
- Клиент: `DataTransferClient` (`ListFormatsAsync`, `ExportAsync` возвращает `byte[]`), метод `SendForUserBytesAsync` в `BaseClient`.
- Не проверено вручную: потоковая отдача большого файла через Kestrel и поведение при обрыве; интеграционные тесты `Freem.Domain.UseCases.IntegrationTests` (`ExportDataUseCase`) и `Freem.Api.Public.IntegrationTests` (`DataTransfer`) только собираются.

- Открытый вопрос (решение отложено пользователем): имена доменных типов запросов `RequestTypes.Export.Data` (`export.data`) и `RequestTypes.Formats.List`; возможный вариант — группа `DataTransfer` с `Export` и `ListFormats`, как в API-слое.

Проверено: `dotnet build Freem.sln` без ошибок; unit-тесты (`Freem.Domain.UnitTests` 243, `Freem.Domain.UseCases.UnitTests` 36, `Freem.Time.UnitTests` 122, `Freem.Domain.Storage.PostgreSQL.UnitTests` 66,
`Freem.Domain.Storage.PostgreSQL.Migrations.UnitTests` 4) проходят.
