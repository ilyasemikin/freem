# Этап: применение выбранных строк

Автор: Claude Code, claude-opus-5-5, 2026-10-23

См. общий контекст и место этого этапа: `plans/data-transfer/general/roadmap.md` (этап 4).

## Зачем именно так

Целевой сценарий пользователя: загрузил файл, один раз на импорт сопоставил активности (и теги, если они есть в файле) с уже существующими в Freem, дальше сохраняет выбранные строки как записи.
Поэтому этап даёт ровно две вещи: сопоставление источника с существующими сущностями, которое хранится в импорте, и создание записей из выбранных строк по набору id. Активности и теги при
импорте не создаются: недостающие пользователь заводит обычным образом. У строк нет статуса и дедупликации (решение пользователя 2026-10-23), поэтому одно применение — «всё или ничего» в одной
транзакции, с пакетной записью вместо тысяч вызовов `CreateRecordUseCase`.

## Зафиксированные факты

Проверено чтением кода (`_Src/Freem`):

- Хранилище импорта (этап 2) хранило для источника решение `ImportActivityResolution`/`ImportTagResolution` («существующая» или «создать новую», колонки `create_new` и `resolved_*_id` с
  `ON DELETE SET NULL`); методы `SetActivityResolutionAsync`/`SetTagResolutionAsync` не проверяют владельца, это оставлено на use case. Use case'ов и API для них не было.
- `CreateRecordUseCase` пишет запись (`IRecordRepository.CreateAsync`, свой `SaveChanges`) и событие `records.created` по одной; пакетного создания записей и событий не было.
- Принадлежность активностей и тегов записи пользователю нигде не проверяется (внешние ключи связей только по id).
- `Record`: от 1 до 16 активностей, до 64 тегов, периоды строго положительной длительности и без пересечений; `RelatedIdsCollection` молча схлопывает повторы.
- Строка Time Tracker может иметь начало, равное концу (решение пользователя этапа 3); из неё `Record` создать нельзя.
- Блокировки: `ILocker` (Redis), `LockerExtensions` берёт блокировку на 2 минуты.

## Один-два иллюстративных примера (не исчерпывающий список!)

- Импорт Time Tracker с 5 активностями: пользователь сопоставляет их с пятью своими активностями и сохраняет две строки по id, получает две записи; позже сохраняет остальные строки тем же сопоставлением.
- Выбраны 3 строки, одна с началом, равным концу: создаются 2 записи, id третьей строки возвращается в списке пропущенных.

## Направление решения (не пошаговая реализация)

Согласовано пользователем 2026-10-23:

- **Сопоставление.** У активности и тега импорта хранится `MappedActivityId`/`MappedTagId` (null — не сопоставлено). Use case и `PUT api/v1/imports/{id}/activities/{importActivityId}` (то же для `tags`)
  с телом `{activityId}` (`{tagId}`): id существующей сущности пользователя или null для снятия сопоставления. Проверки: импорт свой, ключ есть в импорте, сущность принадлежит пользователю.
- **Применение.** `POST api/v1/imports/{id}/apply` с ровно одним из `all` и `rowIds`. Все ключи источника, на которые ссылаются выбранные строки, должны быть сопоставлены, иначе ошибка со списком
  ключей и ничего не пишется. Записи создаются в одной транзакции пачками, событие `records.created` на каждую; строки, из которых нельзя создать запись, пропускаются и возвращаются в ответе.
  Статус документа не меняется, повторное применение создаёт дубли.

## Решения пользователя (2026-10-23)

1. Событие `records.created` на каждую созданную запись, вставка пакетная.
2. Строки, из которых нельзя создать запись, пропускаются; в ответе число записей и id пропущенных строк.
3. Применение синхронное, в одном запросе и одной транзакции, с верхним пределом числа строк; замер времени не делается.
4. Сопоставление только с существующими активностями и тегами, задаётся один раз на импорт; сохраняются строки по набору id без правок. «Создать новую» убрано полностью, включая код этапов 2-3
   (доменные `ImportActivityResolution`/`ImportTagResolution`, колонку `create_new`, поле `resolution` ответа API). Суффикс `/resolution` в маршрутах и отдельные `DELETE` не нужны.

## Явно не входит в этот файл (пока)

Создание активностей и тегов из источника, автоподбор сопоставления по названию, дедупликация и ссылка записи на строку импорта, фильтры строк, отмена применения, фоновое применение, фронтенд (этап 5).
Проверка владельца активностей и тегов в обычном `CreateRecordUseCase` (существующий пробел, не относится к импорту).

## Критерий готовности

- `dotnet build Freem.sln` без ошибок и новых предупреждений, `dotnet test Freem.sln` проходит.
- Unit-тесты: ключи без сопоставления, сопоставление строки в `Record` (несколько периодов со своими смещениями, схлопывание повторных активностей, теги), пропуск нулевой длительности и пересечений.
- Интеграционные тесты use case'ов в `docker/test`: образец целиком даёт 47 записей с сопоставленными активностями и 47 событий; явный список строк; несопоставленный ключ — ошибка без записей;
  чужая активность или тег в сопоставлении — ошибка; чужой импорт недоступен; цепочка «экспорт JSON → импорт → сопоставление → применение» воспроизводит запись; строка нулевой длительности пропускается.
- Интеграционные тесты API: сопоставление и его снятие, применение, неоднозначный выбор строк, 401, 404.

## План реализации

Команды из `_Src/Freem`. После каждого шага `dotnet build Freem.sln` без ошибок. Коммитов нет, пока пользователь не попросит.

1. **Пакетная запись.** `IRecordRepository.CreateManyAsync`, `IEventRepository.CreateManyAsync`, `EventProducer.PublishManyAsync`. Проверка: интеграционные тесты репозиториев.
2. **Сопоставление в домене и хранилище.** `MappedActivityId`/`MappedTagId` вместо решений, `UpdateActivityMappingAsync`/`UpdateTagMappingAsync` в репозитории, миграция `ImportSourceMappings`. Проверка: тесты репозитория, тесты миграций.
3. **Use case'ы сопоставления.** `UpdateImportActivityMappingUseCase`/`UpdateImportTagMappingUseCase` с проверками. Проверка: интеграционные тесты use case'ов.
4. **Сопоставление строк.** `ImportMappingCheck`, `ImportMappings`, `ImportRecordFactory`. Проверка: unit-тесты.
5. **Use case применения.** `ApplyImportUseCase`: выбор строк, предел, проверка сопоставления, транзакция с пачками записей и событий. Проверка: интеграционные тесты use case'ов.
6. **API и клиент.** Эндпоинты, DTO, коды ошибок, методы `ImportsClient`. Проверка: интеграционные тесты API.
7. **Финальный прогон.** Сборка, unit-тесты, `.IntegrationTests` в `docker/test` (запускает пользователь).

## Результат реализации

Шаги 1-7 выполнены. Интеграционные тесты по просьбе пользователя прогнаны локально на Postgres и Redis `develop` (базы `freem_*_test`, см. «Проверка на develop»), а не в `docker/test`. Решения, принятые при реализации:

- **Пакетная запись:** `CreateManyAsync` записей и событий — один `SaveChanges` на вызов; у `PublishManyAsync` одно время события на пачку.
- **Выбор строк в хранилище:** у `ImportRowByDocumentFilter` появился необязательный `Ids`, явный выбор читается пачками по 1000, а не запросом на строку.
- **Сопоставление в хранилище:** колонки `mapped_activity_id`/`mapped_tag_id` (переименованы из `resolved_*_id`, данные сохраняются), `create_new` и проверочные ограничения удалены, `ON DELETE SET NULL`
  остаётся: удаление сопоставленной сущности снимает сопоставление. Миграция `20261023114623_ImportSourceMappings`; прежние миграции не правились.
- **Ошибки:** ключа нет в импорте или сущность чужая/несуществующая → `entity_not_found` (404; в каталог добавлены `ImportActivityId`/`ImportTagId`). Несопоставленные ключи → `import:unmapped_entities` (422,
  детали по каждому ключу). Больше `ApplyImportUseCase.MaxRowsCount` (50 000, выбрано при реализации) → `import:too_many_rows` (422). Строка не из этого импорта → `related_entities_not_found` (422).
  Пустой список → `nothing_to_do` (400), неоднозначный выбор (`all` вместе с `rowIds` или ни одного) → `invalid_request` (400), занятая блокировка → 409.
- **Пропуск строк:** пропускается любая строка, нарушающая инварианты `Record`: неположительная длительность, пересечение периодов, больше 16 активностей или 64 тегов после сопоставления.
- **Блокировка** `imports/<id>` берётся и при сопоставлении, и при применении.
- **Имена (по просьбе пользователя):** операции над сопоставлением называются как обновление сущности-существительного «сопоставление»: `UpdateImportActivityMappingRequest`/`UpdateImportTagMappingRequest` (домен и DTO API), `UpdateImportActivityMappingUseCase`, `IImportDocumentRepository.UpdateActivityMappingAsync`/`UpdateTagMappingAsync`, типы запросов `imports.update-activity-mapping`/`imports.update-tag-mapping`; глагол `Map*` не используется. Маршрут `PUT …/activities/{sourceId}` не менялся.
- **Без слова «source» (по просьбе пользователя, 2026-10-24):** свойства и параметры называются по типу. Запросы сопоставления — `ImportActivityId`/`ImportTagId`; маршруты `{importActivityId}`/`{importTagId}`;
  в ответе API у активности и тега импорта `id` (было `sourceId`), у активности `tagIds` (было `tagSourceIds`), у строки `recordId` (было `sourceId`); в домене `ImportDocumentActivity.Activity`/`ImportDocumentTag.Tag`
  (было `.Source`); ошибка `import:unmapped_entities` (было `import:unmapped_sources`); внутренние классы `ImportMappings`/`ImportMappingCheck` (были `ImportSourceMap`/`ImportSourceUsage`); метод репозитория
  `AddTagsAndActivitiesAsync` (был `AddSourceAsync`, этап 2). Колонки БД переименованы миграцией `20261024073025_ImportEntityKeys` (только переименования, данные сохраняются): `source_id` →
  `import_tag_id`/`import_activity_id`/`import_record_id`, `activity_source_id`/`source_activity_id` → `import_activity_id`, `tag_source_id`/`source_tag_id` → `import_tag_id`; свойства EF-сущностей так же.
- **Активности и теги импорта — отдельные ресурсы (по просьбе пользователя, 2026-10-24):** `ImportDocument` больше не содержит `Tags`/`Activities` и загружается без них; в ответе `GET /imports` и
  `GET /imports/{id}` полей `tags`/`activities` нет. Добавлены `GET api/v1/imports/{id}/activities` и `GET api/v1/imports/{id}/tags` (постранично, `offset`/`limit`, заголовки количества, порядок по ключу из файла),
  use case'ы `ListImportActivityUseCase`/`ListImportTagUseCase`, методы репозитория `FindActivitiesAsync`/`FindTagsAsync` с фильтрами `ImportDocumentActivityByDocumentFilter`/`ImportDocumentTagByDocumentFilter`,
  методы `ImportsClient.ListActivitiesAsync`/`ListTagsAsync`. Загрузка пишет документ, затем активности и теги (`AddTagsAndActivitiesAsync`), затем строки — в одной транзакции. Применение читает активности и теги
  импорта пачками; `ImportMappings`/`ImportMappingCheck` принимают списки, а не документ. Use case'ы сопоставления больше не ищут ключ в документе: при неизвестном ключе репозиторий возвращает
  `entity_not_found` с `ImportActivityId`/`ImportTagId`. Схема БД не менялась.
- **API:** `PUT api/v1/imports/{id}/activities/{importActivityId}` (`{activityId}`), `PUT api/v1/imports/{id}/tags/{importTagId}` (`{tagId}`), `POST api/v1/imports/{id}/apply` (`{all, rowIds}` → `{recordsCreated, skippedRowIds}`).
  В ответе импорта у активностей и тегов вместо `resolution` поля `mappedActivityId`/`mappedTagId`. Клиент: `ImportsClient.UpdateActivityMappingAsync`/`UpdateTagMappingAsync`/`ApplyAsync`.
- **Тесты:** unit — сопоставление (7); интеграционные — репозитории (пакетная запись, откат пачки при ошибке, фильтр по `Ids`, сопоставление и его снятие, снятие при удалении активности),
  `ImportApplyUseCasesTests` (12), `ApplyImportTests` API (7). В API-тестах нет сценария с чужим импортом (инфраструктура на одного пользователя); он проверен на уровне use case'ов.
- **Известные ограничения:** блокировка на 2 минуты, более долгое применение может пересечься со вторым; время применения на десятках тысяч строк не замерялось; трекер изменений EF за одно
  применение копит все созданные записи.

Проверено: `dotnet build Freem.sln` без ошибок (8 предупреждений о null, все в ранее существовавших тестах событий); unit-тесты проходят (`Freem.Domain.UnitTests` 278, `Freem.Domain.UseCases.UnitTests` 61,
`Freem.Time.UnitTests` 122, `Freem.Domain.Storage.PostgreSQL.UnitTests` 66, `Freem.Domain.Storage.PostgreSQL.Migrations.UnitTests` 4).
