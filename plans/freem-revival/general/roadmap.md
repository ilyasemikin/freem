# Возрождение Freem

Автор: Claude Code, claude-sonnet-5-5, 2026-10-18

## Зачем

Freem — персональный тайм-трекер (запуск активности, сохранение записи в БД, последующая аналитика). Проект
не развивался с июня 2025. За это время соседние проекты (StashIt, EgoHub, Trandoma, CSharpUtilities) ушли
вперёд и сформировали рабочие конвенции: net10.0, общие библиотеки `Utilities.*` вместо собственных
реализаций, авторизация через EgoHub, Docker-окружения (`develop`/`service`/`test`), `CLAUDE.md`, планы и
скиллы. Главный ориентир по процессу и конвенциям — StashIt; по стеку хранилища (EF Core + PostgreSQL) и
интеграции с EgoHub ближе Trandoma и сам EgoHub.

Состояние на 2026-10-18 (проверено по коду): `dotnet build Freem.sln` собирает всё, кроме трёх
`.IntegrationTests` проектов, которым нужен нерепозиторный `configuration.json` (у `FunctionalTests`, наоборот,
`configuration.json` закоммичен); 67 проектов, из них в решении только 65 — `Freem.Http` (net8.0, на него никто
не ссылается) и `Freem.Entities.Events.InPlace` (один `.csproj` без кода) в решение не входят; остальные на
net9.0, SDK 10; EF Core/Npgsql 8.0.4; смешанный тестовый
стек (xunit разных версий + NUnit); собственные реализации результатов, блокировок, времени, токенов и
собственная подсистема пользователей/JWT (аналогов блокировок и токенов в CSharpUtilities нет); хост (`Freem.Web.Api.Public/Program.cs`) зависит от PostgreSQL,
Redis и Kafka, причём публикация в Kafka (`KafkaEventPublisher`) выполняется внутри use case'ов и без
доступного брокера блокирует запрос; схема БД применяется вручную (`dotnet ef database update`, 20 миграций); есть только `Dockerfile` API, Docker Compose нет; в git закоммичены пароль БД и адреса
(`appsettings.Development.json`, `FunctionalTests/configuration.json`); фронтенд — React 19 + Vite +
PrimeReact, адрес API зашит в код.

Решения пользователя (2026-10-18):

- Идентификация в итоге переезжает на EgoHub. Первым шагом собственная авторизация удаляется целиком, а
  `userId` временно берётся из query (в `UseCaseContextProvider`) — до интеграции с EgoHub.
- Эндпоинт регистрации пользователя на стороне Freem остаётся (после интеграции с EgoHub пользователь создаётся
  через EgoHub, но точка создания пользователя и его настроек в Freem сохраняется). Цепочка существующих
  EF-миграций сохраняется. Единственное допустимое изменение БД во всём плане — удаление сущности паролей
  (таблицы учётных данных пользователя) одной новой миграцией. Если по ходу работы обнаружится что-либо ещё,
  требующее изменения БД или схемы хранения, исполнитель обязан остановиться и согласовать это с пользователем.
- До этапа 6 интеграционные тесты (требующие БД/Redis) не считаются критерием готовности этапов; критерий —
  сборка и unit-тесты.
- Проект личный, сохранность существующих данных не важна: миграция данных не нужна, БД можно создавать с нуля.
- Kafka удаляется. Redis пока остаётся.
- Фронтенд остаётся на Vite + PrimeReact. CI не нужен; нужны Docker Compose окружения по образцу соседних
  проектов, включая `test`. Интеграционным тестам выделяется отдельная база.
- Архитектурная стабилизация (разделение `Domain`/`Domain.Entities`, Events, UseCases, именование слоёв)
  вынесена в отдельный план `plans/freem-architecture/general/roadmap.md` (пока набросок).

## Этапы

1. **Базовая линия.** Получить воспроизводимые сборку и тесты: определить, что считается «тестами» (unit без
   инфраструктуры), решить вопрос с `configuration.json` у интеграционных проектов, прогнать фронтенд
   (`npm ci`, `build`, `lint`), зафиксировать, что проходит, разобрать предупреждения компилятора (по чистой пересборке), решить судьбу
   проектов вне решения (`Freem.Http`, `Freem.Entities.Events.InPlace`) и унифицировать имена файлов-примеров
   конфигурации.
   → `plans/freem-revival/stages/01-baseline.md`.
2. **Удаление собственной авторизации.** Убрать пароли, JWT, токены и их блэклист вместе с соответствующими
   use case'ами, контроллерами и тестами. `userId` временно берётся из query прямо в `UseCaseContextProvider`
   (единая точка создания контекста use case'ов, без правки контроллеров). Регистрация пользователя и
   настройки пользователя (`DayUtcOffset` нужен статистике) остаются; сущность паролей удаляется из
   хранилища (единственное изменение БД, одна миграция), всё остальное в БД не меняется без согласования
   с пользователем. Привести клиентов API, тесты и фронтенд в рабочее состояние без логина. В исследовании этапа
   нужно уточнить: что именно принимает оставшаяся регистрация (без пароля), что делать с полем логина (сейчас оно
   хранится только в таблице паролей), откуда фронтенд берёт `userId`. Временная схема не должна
   публиковаться наружу. → `plans/freem-revival/stages/02-remove-auth.md`.
3. **Удаление Kafka.** Убрать публикацию и потребление событий через Kafka вместе с конфигурацией и
   зависимостями; Redis (блокировки) остаётся. Нужно решить, чем заменяется `IEventPublisher`, который
   обязателен для хоста; журнал событий в БД сохраняется. Согласовать с этапом 2 набросочного плана
   архитектуры, чтобы не делать работу дважды. → `plans/freem-revival/stages/03-remove-kafka.md`.
4. **Платформа и зависимости.** Переход на net10.0 (как в StashIt, EgoHub, Trandoma), обновление EF Core/Npgsql
   (риск: перегенерация миграций и snapshot), `Dockerfile`, тестовых и прочих пакетов, унификация тестового
   стека. → `plans/freem-revival/stages/04-platform.md`.
5. **Общие библиотеки.** Определить, какие собственные `Freem.*` библиотеки заменяются на пакеты `Utilities.*`
   из CSharpUtilities, а какие остаются; выбрать механизм получения пакетов и порядок замены.
   → `plans/freem-revival/stages/05-shared-libraries.md`.
6. **Инфраструктура.** Docker Compose окружения `develop`/`service`/`test` с портами из пула 10150–10199,
   отдельная база для интеграционных тестов с применением миграций в окружении, защита очистки таблиц от
   запуска на нетестовой базе, порт API хоста и адрес API во фронтенде из пула, конфигурация через `.env`, секреты вместо закоммиченных значений (пароль, попавший в историю git, сменить). → `plans/freem-revival/stages/06-infrastructure.md`.
7. **Интеграция с EgoHub.** Заменить временный `userId` из query на аутентификацию через EgoHub и связать
   идентичность EgoHub с локальным пользователем Freem; привести фронтенд и тесты к новой схеме.
   → `plans/freem-revival/stages/07-egohub.md`.
8. **Фронтенд.** Аудит `Freem.Web` на Vite + PrimeReact: актуализация зависимостей, структура каталогов,
   линтер, соответствие текущему API. → `plans/freem-revival/stages/08-web.md`.
9. **Развитие продукта.** После актуализации — backlog функциональности (аналитика, идеи).
   → `plans/freem-revival/stages/09-product.md`.
