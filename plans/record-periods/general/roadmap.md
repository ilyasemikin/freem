# Периоды записи

Автор: Claude Code, claude-sonnet-5-5, 2026-10-20

## Зачем

Сейчас запись (`Record`) хранит ровно один период (`DateTimePeriod Period`, в БД пара `StartAt`/`EndAt`).
Задача, которую прерывают и возобновляют в течение дня, приходится вести несколькими записями с одинаковыми
названием, описанием и тегами. Цель — позволить одной записи содержать несколько периодов, у каждого из
которых может быть своё описание.

Решения пользователя (2026-10-20):

- Период — отдельная сущность и в БД, и в домене: свой `RecordPeriodId`, `DateTimePeriod` и необязательное
  описание периода (отдельный value object, по аналогии с `RecordDescription`). Отдельного «типа» периода нет.
- Над периодами есть отдельные операции API (добавить, изменить, удалить период записи), чтобы потребителю
  не приходилось пересылать список целиком.
- БД пустая, обратная совместимость не нужна: переноса существующих записей, чтения старого формата событий
  и поддержки старого поля `period` в API не будет; схему и контракты можно менять напрямую.

Предварительные архитектурные соображения (уточняются в исследовании этапа 1):

- Период — дочерняя сущность агрегата `Record`, а не самостоятельный агрегат: у него нет собственного
  репозитория, а инварианты (список не пуст, периоды не пересекаются, порядок) проверяет `Record` в одной
  транзакции. Отдельный агрегат потребовал бы свои события и блокировки и защиту инварианта триггером в БД.
- Затрагивается всё, что сегодня опирается на `Record.Period`: события создания и обновления записи,
  сортировка и фильтр по периоду, keyset-пагинация списка
  записей, `TimeStatisticsCalculator` (рассчитан на непрерывную запись), DTO и публичный API (ломающее
  изменение, без совместимости), клиент API, фронтенд (редактор записи, группировка по дням, кэши).
- Простая альтернатива без новой сущности (группа/связь между записями) рассмотрена и отклонена
  пользователем.

## Этапы

1. **Домен и хранилище.** `RecordPeriod` как дочерняя сущность `Record`, коллекция периодов с инвариантами,
   таблица периодов в БД и миграция (данных для переноса нет), события со списком периодов, репозиторий,
   фильтр и порядок списка записей. Запись пока можно создавать и менять через существующие use case'ы с
   одним периодом. → фактура в `plans/record-periods/stages/01-domain-storage.md`.
2. **Use case'ы, API и статистика.** Use case'ы и эндпоинты над периодами записи (добавить, изменить,
   удалить), перевод создания/обновления/чтения записи на список периодов, DTO, клиент API, OpenAPI,
   пересчёт статистики на периоды. → фактура в `plans/record-periods/stages/02-usecases-api-statistics.md`.
3. **Фронтенд.** Редактор записи с несколькими периодами и их описаниями, список и группировка записей по
   дням (запись, пересекающая полночь, или несколько периодов в разные дни), кэши, статистика.
   → фактура в `plans/record-periods/stages/03-frontend.md`.
