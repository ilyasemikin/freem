# Этап: фронтенд

Автор: Claude Code, claude-sonnet-5-5, 2026-10-20

См. общий контекст и место этого этапа: `plans/record-periods/general/roadmap.md` (этап 3).

## Зачем именно так

После этапа 2 публичный API работает с набором периодов (`periods`), а фронтенд всё ещё ожидает одно поле `period` в записи:
он не создаёт, не обновляет и неправильно показывает записи. Этап возвращает фронтенд в рабочее состояние и добавляет то, ради чего
затевались периоды: ввод нескольких периодов с описаниями и их отображение. Обратной совместимости нет, поэтому старый вариант
(одно поле периода) не сохраняется.

## Зафиксированные факты

Проверено по коду и запуском (2026-10-20, после коммита `8d05eb6`):

- Стек: React 19, Vite, PrimeReact, `react-router` 8. Базовая линия: `npx tsc -b` и `npx eslint .` в `Freem.Web` проходят без ошибок и
  предупреждений (поэтому после смены API они всё ещё зелёные: типы фронтенда описаны отдельно и от API не зависят).
- Клиент: `src/clients/RecordsClient.ts` (методы `create`, `update`, `remove`, `get`, `list`, `listByPeriod`, `start`/`stop`/`updateRunning`/...),
  модели в `src/clients/models/records`: `CreateRecordRequest` и `RecordResponse` содержат `period: string` (строка `"<iso>, <iso>"`),
  `UpdateRecordRequest` — `period?: UpdateField<string>`. `UpdateField<T>` — `{value?: T}`; отсутствие `value` в JSON означает очистку.
- Сущности и кэш: `src/entities/RecordEntity.ts` (`period: DateTimePeriod`), `src/cache/entities/RecordsEntitiesCache.ts` (`map` парсит `response.period`
  через `DateTimePeriod.parse`, загружаются только `listByPeriodRequest`).
- Модель времени: `src/data/DateTimePeriod.ts` (`startAt`, `endAt`, `duration` в секундах, `toString()` в формате ISO через `toISOString()`, т.е. с миллисекундами;
  допускает нулевую длину, сервер её отклоняет).
- Экраны записей `src/pages/records`: `RecordsDashboard` (загрузка по периоду дат, создание `RecordAddModal` → `CreateRecordRequest`),
  `RecordList` (обновление и удаление записи, `UpdateRecordRequest` с `period`), `RecordListGrouped` (группировка по дате `record.period.startAt`),
  `RecordPanel` (время «начало - конец» и `DateTimePeriodDurationPanel`, раскрытая часть — заглушка «Information»), `RecordEditor`
  (поля имя, описание, два выбора даты и времени, активности, теги; результат `IRecordEditorData.period: DateTimePeriod`),
  `RecordAddModal`/`RecordUpdateModal` (оболочки редактора). В `RecordEditor` поле описания (`InputTextarea`) не получает `value` из состояния
  (при редактировании записи описание не подставляется).
- Прочие потребители `RecordEntity`/периода записи за пределами `src/pages/records`, кэша и моделей отсутствуют; статистика и running record
  (`RunningRecordEntity`) работают с другими типами и API не изменились.
- Ручной прогон в браузере по правилу проекта выполняется только по согласованию.

## Один-два иллюстративных примера (не исчерпывающий список!)

- `RecordResponse.period: string` → `periods: [{id, period, description?}]`; в `RecordEntity` — список `RecordPeriodEntity`.
- `RecordPanel` вместо `record.period` показывает охватывающее время (начало первого - конец последнего), суммарную длительность периодов
  и в раскрытой части — список периодов.

## Направление решения (не пошаговая реализация)

- **Модели и клиент.** Новые модели (`RecordPeriodRequest`, `RecordPeriodResponse`, `AddRecordPeriodResponse`, `UpdateRecordPeriodRequest`),
  `CreateRecordRequest.periods`, `RecordResponse.periods`, `UpdateRecordRequest` без `period`; методы `RecordsClient.addPeriod/updatePeriod/removePeriod`.
- **Сущности и кэш.** `RecordPeriodEntity {id, period, description?}`; `RecordEntity.periods` (по возрастанию начала) и вычисляемые начало, конец,
  суммарная длительность; `RecordsEntitiesCache.map` разбирает `periods`.
- **Отображение.** `RecordPanel`: диапазон «первый старт - последний конец», суммарная длительность (сумма периодов, а не разница крайних точек), пометка
  числа периодов, если их больше одного; раскрытая часть — список периодов (время, длительность, описание).
- **Создание.** `RecordAddModal`/`RecordEditor` создаёт запись со списком периодов: одна строка по умолчанию, можно добавлять и удалять строки (начало, конец,
  описание). Проверки на клиенте: хотя бы один период, конец позже начала (нулевая длина запрещена), периоды не пересекаются (касание допустимо).
- **Правка существующей записи.** См. открытый вопрос 1.
- **Группировка.** См. открытый вопрос 2.
- **Исправление попутно.** Подставлять значение описания записи в `InputTextarea` при редактировании (иначе описание теряется или не показывается).

Решения пользователя (2026-10-20):

1. Правка периодов существующей записи — вариант (B): диалог правки меняет имя, описание, активности и теги, а периоды редактируются списком в том же
   диалоге отдельными действиями (на каждой строке «Сохранить» и «Удалить», кнопка «Добавить период»), каждое действие сразу вызывает свою операцию API.
2. Группировка по дням остаётся по дате начала первого периода (запись показывается один раз).
3. В панели списка: диапазон «первый старт - последний конец» и суммарная длительность периодов.
4. Попутно исправить подстановку описания записи в `RecordEditor`.
