# Единый часовой пояс пользователя

Автор: Claude Code, claude-sonnet-5-5, 2026-10-21

## Зачем

При ручном прогоне фронтенда после инициативы «Периоды записи» (`plans/record-periods`) выяснилось, что время считается и показывается в разных часовых поясах,
а настройка пользователя `DayUtcOffset` (на этапе 2 переименована в `TimeZoneOffset`) на бэкенде работает не так, как называется. Состояние на 2026-10-21 (проверено по коду и ручным прогоном в браузере в поясе UTC+3):

- Фронтенд: поля ввода времени (PrimeReact `Calendar`) работают в локальном времени браузера, а `DateHelper.toFormattedString` показывает время записей в UTC (введённое
  10:00 отображалось как 07:00). Группировка записей по дням использует локальные даты. Диапазон записи, охватывающей несколько суток, выводится без дат («17:00 - 08:00»).
- Список записей по дню: фронтенд отправляет даты без времени (`2026-10-21, 2026-10-22`), сервер разбирает их как период по UTC. Из кода следует, что запись между локальной полуночью и
  03:00 в поясе UTC+3 попадает в сутки UTC предыдущего дня (запуском не проверено).
- Бэкенд: настройка `DayUtcOffset` хранится и меняется через `api/v1/user/settings`, статистика по дням (`StatisticsPerDaysUseCase`) считает начало суток как `00:00 UTC + offset`
  (`TimeOnly.MinValue.Add(offset)`). Это обратное смещение (для настройки `+03:00` сутки начинаются в 03:00 UTC, как в поясе UTC−3), а для отрицательного смещения `TimeOnly.Add` не уходит
  в предыдущие сутки, а заворачивается в пределах той же даты. Для нуля всё верно; тесты используют только `+01:00`/`+03:00` как произвольные значения. Во фронтенде есть только модели
  и методы клиента настроек, интерфейса настроек и использования смещения нет.

Решения пользователя (2026-10-21):

- Часовым поясом пользователя считается `TimeZoneOffset` из его настроек. Вся логика (границы суток, статистика, показ и ввод времени во фронтенде, диапазоны записей) работает
  относительно него, значение по умолчанию `+00:00` (UTC). Настройка меняется на отдельной странице во фронтенде.
- Семантика `TimeZoneOffset` — обычное смещение пояса от UTC (`+03:00` — Москва): сутки D — это `[D 00:00 - offset, D 00:00 - offset + 24 ч)` по UTC. Исправляется статистика по дням.
- Для историчности смещение сохраняется в каждом периоде записи (его проставляет сервер из текущей настройки при создании периода и при изменении его времени; правка только описания
  смещение не меняет), но в логике не используется: все данные показываются и считаются по текущей настройке. К идее «показ по смещению записи» можно вернуться позже.
- Единый подход: все методы (сервер и клиент) интерпретируют время относительно настройки пользователя; API работает с моментами времени (`DateTimePeriod` с точным временем), границы
  суток для списков фронтенд считает сам по текущему смещению.
- Диапазон записи, охватывающей несколько суток, показывает дату у конца, если он на другом дне.

## Этапы

1. **Семантика смещения и серверные границы суток.** Привести смещение (`TimeZoneOffset`) к смыслу «смещение пояса от UTC»: исправить границы суток в статистике (по дням и по другим периодам, если они зависят
   от смещения), определить допустимый диапазон значения и покрыть тесты положительными и отрицательными смещениями. Значение по умолчанию и нулевое смещение не меняют поведения.
   → фактура в `plans/timezone/stages/01-offset-semantics.md`.
2. **Смещение в периодах записей.** Хранить смещение в периоде (БД, домен, снимок в событиях), проставлять его на сервере из настройки пользователя при создании и изменении времени периода
   (в том числе при остановке running record), отдавать его в ответах API как справочное значение; в логике оно не участвует.
   → фактура в `plans/timezone/stages/02-period-offset.md`.
3. **Время во фронтенде.** Страница настроек со сменой смещения; загрузка настройки; единый показ и ввод времени в поясе пользователя (включая поля `Calendar`); границы суток для списка записей
   из смещения и отправка их точными моментами; диапазон записи с датой у конца на другом дне; устранение расхождения UTC и локального времени.
   → фактура в `plans/timezone/stages/03-frontend-time.md`.
