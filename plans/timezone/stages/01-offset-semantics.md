# Этап: семантика смещения и серверные границы суток

Автор: Claude Code, claude-opus-5-5, 2026-10-21

См. общий контекст и место этого этапа: `plans/timezone/general/roadmap.md` (этап 1).

## Зачем именно так

`DayUtcOffset` становится часовым поясом пользователя, от него дальше зависят периоды записей (этап 2) и фронтенд (этап 3).
Поэтому смысл значения и границы суток надо сначала закрепить на сервере в одном месте и покрыть тестами, а потом строить на них остальное.
Расчёт начала суток выносится в один метод, чтобы статистика по дням и по периодам не считала его каждая по-своему (сейчас код
продублирован и ошибка повторяется в обоих местах).

## Зафиксированные факты

- `DayUtcOffset` (`Freem.Domain/Users/Models/DayUtcOffset.cs`) — обёртка над `TimeSpan` без ограничений на значение. Строковый формат —
  `TimeSpan` `"c"`: `03:00:00`, `-05:30:00`, без знака `+` у положительных. Тот же формат используется в JSON (`ParsableJsonConverter<DayUtcOffset>`),
  в payload события `UserSettingsChangedEvent` и в API `api/v1/user/settings`. В БД хранится как `UtcOffsetTicks` (`UserMapper`).
  `TryParse` принимает любой `TimeSpan` в формате `"c"`, в том числе `1.00:00:00` (сутки) и дробные секунды.
- Смещение участвует в логике только в двух местах, и в обоих одинаково:
  `var time = TimeOnly.MinValue.Add(settings.DayUtcOffset.Value); date.ToUtcDateTime(time)`:
  - `StatisticsPerDaysUseCase`: сутки `[D + time, D + 1 + time)` по UTC, а ключ словаря результата — `current.ToDateOnly()`, то есть дата начала суток по UTC;
  - `StatisticsPerPeriodUseCase` (день/месяц/год через `IStatisticsPeriod.ToDatePeriod()`, конец исключающий): `[start + time, end + time)`.
- Ошибки текущей формулы: при `+03:00` сутки начинаются в 03:00 UTC (обратный знак); при отрицательном смещении `TimeOnly.Add` заворачивает
  время в пределах суток (`-05:00` → 19:00 той же даты), то есть получается ещё и сдвиг на день. Для `00:00:00` результат верный.
- Если просто исправить знак, ключ словаря в `StatisticsPerDaysUseCase` сломается: для `+03:00` сутки D начинаются в `D-1 21:00 UTC`, и
  `current.ToDateOnly()` вернёт `D-1`. Ключ надо брать из перебираемой даты, а не из момента UTC.
- Других серверных мест, где смещение влияет на логику, нет (поиск `DayUtcOffset` по решению): список записей по периоду принимает
  `DateTimePeriod`/даты без участия настройки, это область этапа 3.
- Тесты: `StatisticsPerDaysUseCaseTests` и `StatisticsSeveralPeriodsUseCaseTests` (`Freem.Domain.UseCases.IntegrationTests`) работают со
  смещением по умолчанию; `+01:00`/`+03:00` встречаются только в тестах обновления настроек и сериализации событий как произвольные значения.
  Модульные тесты `DayUtcOffsetTests` проверяют только разбор и формат.

## Один-два иллюстративных примера (не исчерпывающий список!)

- Пользователь с `03:00:00` (Москва), статистика за 2025-03-10: сейчас считается `[2025-03-10 03:00, 2025-03-11 03:00)` UTC, после этапа —
  `[2025-03-09 21:00, 2025-03-10 21:00)` UTC, ключ `2025-03-10`.
- Пользователь с `-05:00:00`: сейчас `[2025-03-10 19:00, 2025-03-11 19:00)` UTC, после этапа — `[2025-03-10 05:00, 2025-03-11 05:00)` UTC.

## Направление решения (не пошаговая реализация)

- Один метод расчёта начала суток D для смещения: `D 00:00 UTC − offset` (например метод `DayUtcOffset`, возвращающий UTC `DateTime` для
  `DateOnly`). Обе статистики считают границы через него; `StatisticsPerDaysUseCase` берёт ключ из перебираемой даты.
- Допустимый диапазон: `[-12:00, +14:00]` (реальные пояса), значение кратно минуте. Проверка в конструкторе (`ArgumentOutOfRangeException`)
  и в `TryParse` (`false` → `FormatException` → 400 в API, по правилу из CLAUDE.md).
- Строковый формат `"c"` не меняется (открытый вопрос ниже).
- Тесты: модульные на расчёт границ суток (`0`, положительное, отрицательное, нецелое `05:30`/`-05:30`) и на диапазон;
  интеграционные use case статистики по дням и по периоду с положительным и отрицательным смещением (сдвиг записи через границу суток).

Решения пользователя (2026-10-21):

1. Строковый формат `"c"` (`03:00:00`, `-05:30:00`) остаётся.
2. Диапазон `[-12:00, +14:00]` с точностью до минуты.
3. Реальных данных нет (сервис на доработке), миграция сохранённых значений не нужна.

## Критерий готовности

- `dotnet build Freem.sln` без новых предупреждений, `dotnet test Freem.sln` (модульные) зелёные, в том числе новые тесты границ суток и диапазона.
- `Freem.Domain.UseCases.IntegrationTests` (и при изменении API `Freem.Api.Public.IntegrationTests`) зелёные в `docker/test`, включая
  новые тесты статистики с положительным и отрицательным смещением; прогон делает пользователь.
- `PUT api/v1/user/settings` со значением вне диапазона возвращает 400.
- Для смещения `00:00:00` поведение статистики не меняется (существующие тесты проходят без правок).

## План реализации

1. `DayUtcOffset`: проверка диапазона и кратности минуте в конструкторе и `TryParse`, метод начала суток для даты.
   Модульные тесты в `DayUtcOffsetTests`. Проверка: `dotnet build`, `dotnet test` модульных тестов.
2. `StatisticsPerDaysUseCase` и `StatisticsPerPeriodUseCase` считают границы через новый метод; ключ дня — перебираемая дата.
   Проверка: `dotnet build`, существующие модульные тесты.
3. Интеграционные тесты use case: статистика по дням и по периоду с положительным и отрицательным смещением; тест API на 400 при
   смещении вне диапазона. Проверка: сборка тестовых проектов; прогон в `docker/test` делает пользователь.
