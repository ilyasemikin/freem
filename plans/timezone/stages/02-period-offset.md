# Этап: смещение в периодах записей

Автор: Claude Code, claude-opus-5-5, 2026-10-21

См. общий контекст и место этого этапа: `plans/timezone/general/roadmap.md` (этап 2).

## Зачем именно так

Смещение в периоде нужно только для историчности: по нему позже можно будет показать запись в поясе, в котором она была сделана.
Поэтому его проставляет сервер из текущей настройки пользователя: клиент его не передаёт и подменить не может. В логике
(статистика, пересечения, границы суток) оно не участвует. Значение записывается вместе с периодом: в БД, в доменной сущности и в
снимке события, чтобы история событий оставалась полной.

## Зафиксированные факты

- `RecordPeriod` (`Freem.Domain.Entities/Records/RecordPeriod.cs`): `Id`, `Period` (`DateTimePeriod`), `Description`. Снимок для событий —
  `RecordPeriodSnapshot` (`Freem.Domain/Records/Models`), строится в `Record` (`Record.cs:78`). Payload события —
  `RecordPeriodPayload(Id, StartAt, EndAt, Description)` в `EventPayloadSerializer`, сериализуется массивом JSON в поле `Periods`
  событий `RecordCreatedEvent`/`RecordUpdatedEvent`.
- БД: таблица периодов (`RecordPeriodEntity`, `RecordPeriodEntityTypeConfiguration`) хранит `start_at`, `end_at`, `description`; смещения нет.
  Настройка пользователя хранится как `utc_offset_ticks bigint` (`UserSettingsEntity`); для периода логично хранить так же.
  Последняя миграция `20261020101405_RecordPeriods`; `dotnet ef` 10.0.11 доступен.
- Периоды создаются или меняются в трёх use case:
  - `CreateRecordUseCase` через `RecordPeriodsFactory.Create`; сюда же приходит `StopRunningRecordUseCase` (он собирает
    `CreateRecordRequest` и вызывает создание через медиатор), то есть остановка running record отдельной правки не требует;
  - `AddRecordPeriodUseCase`;
  - `UpdateRecordPeriodUseCase`: собирает новый `RecordPeriod` из текущего и запроса (`Period` и `Description` опциональны).
  Ни один из них сейчас не читает настройки пользователя; статистика читает их через медиатор (`GetUserSettingsRequest`).
- API: `RecordPeriodResponse` (`Id`, `Period`, `Description`), маппинг в `Freem.Api.Public.UseCases/.../Mappers/Dtos/RecordMapper.cs`.
  Запросы создания и изменения периода смещение не принимают, и не должны.
- Тип смещения — `DayUtcOffset` (`Freem.Domain.Users.Models`), после этапа 1 проверяет диапазон и умеет считать начало суток.

## Один-два иллюстративных примера (не исчерпывающий список!)

- Пользователь с настройкой `03:00:00` создаёт запись с двумя периодами: оба получают `03:00:00`. Потом меняет настройку на `-05:00:00` и
  правит описание первого периода: его смещение остаётся `03:00:00`. Если он меняет время второго периода, тот получает `-05:00:00`.
- `GET api/v1/records/{id}` возвращает у каждого периода справочное поле со смещением.

## Направление решения (не пошаговая реализация)

- Домен: обязательное свойство смещения в `RecordPeriod` и `RecordPeriodSnapshot`, учёт в равенстве и сравнении.
- Use case создания, добавления и изменения периода получают текущую настройку пользователя (через медиатор, как статистика) и
  проставляют её новым периодам. При изменении периода смещение обновляется, если в запросе есть `Period`, а при правке только
  описания остаётся прежним.
- БД: колонка `time_zone_offset_ticks bigint not null` в таблице периодов, миграция со значением по умолчанию `0` для существующих строк.
- События: поле смещения в `RecordPeriodPayload`.
- API: поле смещения в `RecordPeriodResponse` (в формате `"c"`, как в настройках), клиент `Freem.Api.Public.Client` получает его вместе с DTO.
- Тесты: модульные (снимок, сериализация payload), интеграционные storage (сохранение и чтение смещения), use case (создание, добавление,
  изменение времени, правка только описания, остановка running record), API (поле в ответе).

Решения пользователя (2026-10-21):

1. Тип `DayUtcOffset` переименовывается в `TimeZoneOffset`: это тот же тип, что в настройках пользователя, теперь он же у периода.
   Свойства тоже называются `TimeZoneOffset` (`UserSettings`, `UpdateUserSettingsRequest`, `UserSettingsChangedEvent`, DTO API), в JSON
   `timeZoneOffset`; колонка настроек в БД — `time_zone_offset_ticks` (переименование в миграции этапа), колонка периода — так же.
   Короткое `Offset` отклонено: в API `offset` уже занят пагинацией.
2. Для уже записанных событий без смещения (`RecordCreated`/`RecordUpdated` и `UserSettingsChanged` со старым ключом) при чтении
   подставляется `00:00:00`.
3. Любой запрос изменения периода с `Period` считается изменением времени, без сравнения со старым значением.

## Явно не входит в этот файл (пока)

- Использование смещения периода в показе или расчётах: по решению пользователя всё считается по текущей настройке.
- Фронтенд (этап 3): интерфейс и использование смещения. Модели клиента (`UserSettingsResponse`, `UpdateUserSettingsRequest`,
  `RecordPeriodResponse`) приводятся к новым полям API в этом этапе, чтобы клиент не расходился с сервером.

## Критерий готовности

- `dotnet build Freem.sln` без новых предупреждений, `dotnet test Freem.sln` (модульные) зелёные.
- Миграция применяется контейнером `postgres-migration` в `docker/test`; интеграционные тесты storage, use case и API зелёные (прогон
  делает пользователь), включая новые тесты на проставление смещения.
- В ответе API у каждого периода есть смещение, равное настройке пользователя на момент создания или последнего изменения времени периода.

## План реализации

1. Переименование `DayUtcOffset` → `TimeZoneOffset` (тип, свойства, запросы, событие, DTO, тесты); чтение `UserSettingsChangedEvent`
   с подстановкой `00:00:00` при отсутствии ключа. Проверка: `dotnet build`, модульные тесты.
2. Домен: `TimeZoneOffset` в `RecordPeriod` и `RecordPeriodSnapshot`, поле в payload событий с подстановкой `00:00:00`.
   Проверка: сборка, модульные тесты сериализации и событий.
3. Storage: свойство и колонка периода, переименование колонки настроек, маппинг, миграция. Проверка: сборка, модульные тесты миграций.
4. Use case: создание, добавление и изменение периода получают настройку через медиатор и проставляют смещение.
   Проверка: сборка; интеграционные тесты use case на все случаи из «Направления».
5. API: поле `TimeZoneOffset` в `RecordPeriodResponse`, маппинг, интеграционный тест ответа. Проверка: сборка; прогон
   интеграционных тестов в `docker/test` делает пользователь.
